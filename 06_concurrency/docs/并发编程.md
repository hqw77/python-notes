# 01 并发 + 并行 + GIL
## 概念
### 并发：
多个任务“交替”执行，宏观上看起来是同时进行，微观上其实是轮流使用 CPU

单核CPU就能实现并发

### 并行：
多个任务真正”同时“执行

必须多核CPU（4 核 CPU 最多同时跑 4 个真正的并行任务）

### GIL（全局解释器锁）
Global Interpreter Lock 是CPython 解释器（Python 默认解释器）

+ **核心规则**：**在任何时刻，只允许一个线程执行 Python 字节码。**

**解释器（****Interpreter****）**是一种计算机程序，它**逐行读取、翻译并立即执行**源代码，而不像编译器那样先把整个程序翻译成机器码再运行。

解释器的工作流程通常是：

1. **读取**一行（或一个语句）源代码
2. **解析**成内部数据结构（如抽象语法树）
3. **立即执行**该语句
4. 重复上述过程，直到程序结束

关键特征是：**翻译和执行是交替进行的**，不会生成独立的可执行文件。

| 对比项 | 解释器 | 编译器 |
| --- | --- | --- |
| 翻译方式 | 逐行翻译并立即执行 | 一次性翻译整个程序 |
| 输出 | 不生成独立可执行文件 | 生成目标代码/可执行文件 |
| 执行速度 | 通常较慢（每次运行都要翻译） | 运行速度快（已提前编译） |
| 调试便利性 | 错误可定位到具体行，调试方便 | 编译期报错，运行时错误较难定位 |
| 跨平台性 | 有解释器即可运行 | 需针对平台重新编译 |

#### 影响
GIL 限制了同一时刻只有一个线程能跑

##### CPU 密集型任务（计算）
+ **特征**：大部分时间在“算”（例如：死循环、图像处理、加密解密、大数据计算），CPU 满载。
+ **GIL 的表现**：**灾难**。即便你开 4 个线程，它们也会为了抢夺唯一的 GIL 锁而疯狂“打架”。线程切换本身也有开销，最终导致**多线程跑计算任务，反而比单线程更慢！**

##### I/O 密集型任务（输入/输出）
+ **特征**：大部分时间在“等”（例如：网络请求、读写磁盘/数据库、等待用户输入），CPU 闲着。
+ **GIL 的表现**：**完美**。当线程 A 发起网络请求等待响应时，它会**主动释放 GIL 锁**，让线程 B 去干活。因此，多线程非常适合 I/O 密集任务。

#### 常见误区
+ ❌ **误区 1：“多线程一定比单线程快”**
    - ✅ **真相**：在 CPU 密集任务下，多线程因为 GIL 和线程切换开销，表现往往不如单线程。
+ ❌ **误区 2：“Python 不能实现并行”**
    - ✅ **真相**：Python 的多进程可以绕过 GIL，实现真正的多核并行。
+ ❌ **误区 3：“GIL 是 Python 的致命缺陷”**
    - ✅ **真相**：这是 CPython 为了简化内存管理（避免多线程内存回收崩溃）做出的历史设计妥协。如今可以用多进程绕过 GIL；无 GIL 的实现有 Jython、IronPython，CPython 3.13+ 也提供了实验性的 free-threaded 构建（PEP 703）。

# 02 线程基础---threading 模块
核心目标：学会如何让多个任务”同时“跑，以及如何控制它们

## 为什么需要多线程
默认情况下，Python 程序是一条直线往下执行的（单线程）。如果中间有一个任务需要等待网络 3 秒，整个程序就会在这里卡住 3 秒。
**开一个线程，就能让它在后台去等，主线程继续往下干活。**

💡 **线程的本质**：同一个进程里的一条独立执行流。线程之间**共享内存**（变量），所以通信极方便，但这也引出了后续的“数据竞争（Data Race）”问题

## 核心 API 速览
| API / 属性 | 作用 |
| --- | --- |
| `Thread(target=fn, args=(...))` | 创建一个线程，`target`是要执行的函数 |
| `.start()` | **启动线程**（真正的入口） |
| `.join()` | 阻塞主线程，直到该子线程执行结束 |
| `.daemon = True` | 设置为**守护线程**（主线程退出时，它会被强制干掉） |
| `threading.current_thread()` | 获取当前正在运行的线程对象 |
| `threading.active_count()` | 获取当前存活的线程数量 |

## 核心案例
### 案例 1：创建线程的两种方式
**直接传函数（最常用）**：
把普通函数传给 `target`，如果有参数就放在 `args` 里（注意是个元组）。

```plain
t1 = threading.Thread(target=worker, args=("A", 1), name="线程A")
t1.start()
```

**继承 **`**Thread**`** 并重写 **`**run**`**（适合需要维护内部状态时用）**：

```plain
class MyThread(threading.Thread):
    def run(self):
        # 你的业务逻辑
```

⚠️ **新手必踩的坑：**`**start()**`** vs **`**run()**`
直接调用 `t.run()`**不会**开新线程！它只是像普通函数一样在当前线程里执行完毕。必须用 `t.start()`，Python 才会去创建新线程并在新线程里调用 `run()`。

### 案例 2：`join()` 的作用 —— 等 vs 不等
+ **不写 **`**join()**`：主线程不管子线程的死活，直接往下走。如果主线程代码跑完了，程序直接退出，子线程可能还没来得及打印结果就被强制终止了。
+ **写了 **`**join()**`：主线程会在 `t.join()` 这一行阻塞（死等），直到子线程跑完，才继续往下执行。
+ **使用场景**：需要收集所有线程的结果再做统计时，必须 `join()`。

### 案例 3：`daemon` 守护线程
+ **普通线程**：主线程结束了，如果普通线程还没跑完，程序会**等**它们跑完才退出。
+ **守护线程 (**`**daemon=True**`**)**：主线程一旦结束，守护线程立刻被**强制终止**（不管它跑到哪了）。
+ **使用场景**：后台日志记录、心跳检测、定时清理垃圾。这些任务不需要阻塞程序的退出。如果不用守护线程，一个 `while True` 的普通线程会让你的程序永远关不掉。

### 案例 4：线程共享变量的陷阱
代码中演示了 4 个线程同时对同一个变量 `counter` 进行 `+= 1` 十万次。

+ **期望结果**：400000。
+ **实际结果**：大概率是 400000（因为 GIL 的存在，且 `counter += 1` 执行太快），但**理论上这是不安全的**。
+ **原理**：`counter += 1` 在底层分为“读取、计算、写回”三步。如果线程 A 读到 `counter=10`，还没写回时 GIL 发生切换，线程 B 也读到了 10 并写回了 11，A 醒来后也会写回 11。两次加法，结果却只加了 1。
+ **结论**：多线程修改共享变量极其危险，必须用锁

# 03 线程锁 Lock/RLock 与竞态条件
## 一、为什么需要锁？
### 1.1 一个“读-改-写”操作并不是一步完成的
在 Python 中，看似简单的一行代码：

```python
counter += 1
```

实际上被拆成了三步：

1. **读**：读取 `counter` 的当前值
2. **改**：把值加 1
3. **写**：把新值写回 `counter`

如果多个线程同时执行这个操作，就可能发生交错：

```plain
线程 A: 读 balance = 100
线程 B: 读 balance = 100   ← A 还没写回，B 读到了旧值
线程 A: 写回 90
线程 B: 写回 90            ← 两次取款只扣了一次钱
```

这就是**竞态条件（race condition）**：程序的正确性依赖于线程执行的先后顺序，而线程调度是不可预测的。

### 1.2 核心概念速查
| 概念 | 解释 |
| --- | --- |
| 竞态条件 | 结果取决于执行顺序，不可预测 |
| Lock | 互斥锁：同一时刻只有一个线程能持有 |
| `acquire()` | 拿锁（阻塞直到拿到） |
| `release()` | 放锁 |
| `with lock:` | 推荐写法，自动 acquire/release，异常也安全 |
| RLock | 可重入锁：同一线程可重复 acquire 不卡死 |
| 死锁 | 两个线程互相等对方放锁，谁都动不了 |

## 二、案例 1：竞态条件——银行取款被“超扣”
### 2.1 场景描述
真实场景：银行取款 = **先查余额 → 判断够不够 → 扣款**。这三步之间有真实的时间间隔。

```plain
balance = 1000

def withdraw_without_lock(amount):
    nonlocal balance
    for _ in range(100):
        if balance >= amount:       # 1. 检查余额够不够
            time.sleep(0.0001)      # 2. 模拟"处理延迟"(这里会被切走!)
            balance -= amount       # 3. 扣款
```

### 2.2 运行结果
```plain
--- 不加锁: 多线程取款, 余额被扣成负数 ---
  余额: -200  ← 应该是 0, 现在是负数!
  (8 个线程同时'检查'发现余额够, 于是都扣款, 超额扣款了)
```

### 2.3 为什么会超扣？
+ 8 个线程同时检查 `balance >= 10`，此时余额都是 1000，判断都通过
+ 然后每个线程都执行 `sleep(0.0001)`，主动让出 GIL
+ 等它们醒来后，都执行 `balance -= 10`，但彼此不知道对方已经扣过款
+ 最终扣款次数超过了余额允许的次数

**关键点**：`sleep()` 主动让出 GIL，把“检查”和“扣款”之间的窗口拉长到足够被其他线程插入。

## 三、案例 2：用 Lock 修复
### 3.1 加锁方案
```plain
balance = 1000
lock = threading.Lock()

def withdraw_with_lock(amount):
    nonlocal balance
    for _ in range(100):
        with lock:                  # 锁住整个"检查+扣款", 别人进不来
            if balance >= amount:
                time.sleep(0.0001)
                balance -= amount
```

### 3.2 运行结果
```plain
--- 加锁: 结果正确 ---
  余额: 0  ← 正确归 0!
```

### 3.3 原理
`with lock:` 保证了“检查余额 + 扣款”这一整段代码是**原子操作**：同一时刻只有一个线程能进入临界区，其他线程必须等待锁释放后才能进入。

**注意**：`with lock:` 等价于 `lock.acquire()` + `try...finally: lock.release()`，异常时也能安全释放锁。

## 四、案例 3：为什么 `counter += 1` 常常“看起来没事”？
### 4.1 经典困惑
你可能试过这个经典例子，却发现结果“意外地正确”：

```plain
counter = 0
def add():
    counter += 1   # 4 个线程各加 100 万次
# 结果却等于 400 万，没丢更新。为什么？
```

### 4.2 原因：GIL 切换粒度
+ CPython 的 **GIL（全局解释器锁）** 每 **5ms** 才切换一次线程
+ 而 `counter += 1` 的“读-改-写”三步加起来只有**几十纳秒**
+ 切换点几乎不可能正好落在“读”和“写”之间

所以朴素的 `counter += 1` 在现代 CPython 上**很难复现竞态**。

### 4.3 但竞态真实存在
案例 1 的取款例子能稳定复现，因为 `sleep(0.0001)` 主动让出 GIL，把间隔拉长到足够被切走。

**结论**：

+ 竞态需要“读-改-写”之间有足够的**窗口**让别的线程插进来
+ `counter += 1` 窗口太小（纳秒级）→ 难复现
+ 取款（检查+扣款）有真实耗时 → 稳定复现
+ **真实项目里，竞态往往藏在“检查+操作”这类有真实耗时的地方**

**警告**：不要因为 `counter += 1` 测试没复现就认为不需要锁——这是幻觉。跨平台、不同 Python 版本、不同负载下都可能出问题。**共享可变状态 + 多线程 → 必须加锁**。

## 五、Lock vs RLock
### 5.1 关键区别
| 特性 | Lock | RLock |
| --- | --- | --- |
| 谁拿的锁只能谁放 | ✅ | ✅ |
| 同一线程再次 acquire | ❌ 卡死（死锁） | ✅ 内部计数，可重复 |
| 释放条件 | 一次 release | 放同样次数才真正释放 |

### 5.2 RLock 的典型场景
一个带锁的函数，内部又调用了另一个带锁的函数：

```plain
def outer():
    with lock:
        inner()        # inner 内部也 with lock

def inner():
    with lock:
        ...
```

+ 用 `Lock`：`inner()` 第二次 acquire 时会卡死（同一线程不能重复拿同一把 Lock）
+ 用 `RLock`：同一线程可以多次 acquire（内部计数），放同样次数才真正释放

### 5.3 演示代码
```plain
def lock_then_lock_again(lock_obj, name):
    with lock_obj:
        print(f"  [{name}] 第一次拿到锁")
        with lock_obj:   # Lock 会在这里卡死; RLock 没事
            print(f"  [{name}] 第二次拿到锁")
```

运行结果：

```plain
--- Lock 重复加锁 → 死锁 (只打印到第一次) ---
  [Lock] 第一次拿到锁
  (Lock 卡死在第二次拿锁, 上面只有第一次的打印)

--- RLock 重复加锁 → 正常 ---
  [RLock] 第一次拿到锁
  [RLock] 第二次拿到锁
```

## 六、死锁：交叉拿锁
### 6.1 场景
两把锁 A、B，两个线程：

```plain
def thread1():
    with lock_a:
        time.sleep(0.1)
        with lock_b:           # 等 lock_b, 但被 thread2 占着
            print("thread1 拿到了两把锁")

def thread2():
    with lock_b:
        time.sleep(0.1)
        with lock_a:           # 等 lock_a, 但被 thread1 占着
            print("thread2 拿到了两把锁")
```

### 6.2 发生了什么
1. `thread1` 拿到 `lock_a`，`thread2` 拿到 `lock_b`
2. `thread1` 等 `lock_b`（被 thread2 占着），`thread2` 等 `lock_a`（被 thread1 占着）
3. 双方互相等待，谁都不释放 → **死锁**

运行结果：

```plain
--- 交叉拿锁 → 死锁 ---
  (两个线程互相等对方, 谁都打印不出来 —— 死锁)
  解法: 所有线程按相同顺序拿锁 (都先 A 后 B)
```

### 6.3 解法
**所有线程按相同顺序拿锁**：都先拿 A 再拿 B（或都先拿 B 再拿 A），就不会出现交叉等待。

## 七、总结与铁律
### 7.1 概念回顾
+ **竞态条件** = 结果取决于线程执行顺序，因“读-改-写”非原子引起
+ **Lock** = 互斥锁，保证“同一时刻只有一个线程”进临界区
+ **RLock** = 可重入锁，同一线程可重复加锁（解决嵌套加锁死锁）
+ `**with lock**` = 推荐写法，自动 acquire/release，异常也安全

### 7.2 四条铁律
1. **共享可变状态 + 多线程 → 必须加锁**
2. **锁的范围越小越好**（只锁必要代码，别把 `sleep` 也锁进去）
3. **多把锁时，所有线程按相同顺序拿锁**，避免死锁
4. **优先用 **`**Queue**`** 等线程安全容器**，能不加锁就不加锁（见 04 章）

### 7.3 常见误区提醒
| 误区 | 纠正 |
| --- | --- |
| “`counter += 1`<br/> 测试没出问题，不用加锁” | 竞态窗口小不等于没有，不同环境都可能触发 |
| “加了锁就万事大吉” | 锁范围太大影响性能，多锁顺序不当会死锁 |
| “Lock 和 RLock 随便选” | 嵌套加锁必须用 RLock，否则死锁 |
| “死锁是偶发问题，不用管” | 死锁是确定性设计缺陷，必须从拿锁顺序上根治 |

# 04 线程同步原语（Semaphore / Event / Condition / Queue）
## 一、为什么锁不够用？
`Lock` / `RLock` 解决的是**互斥**问题——"同一时刻只允许一个线程进临界区"。但现实中的多线程协作远不止"互斥"这一种需求：

| 现实需求 | 对应的同步原语 |
| --- | --- |
| "最多同时只允许 3 个线程访问数据库" | **Semaphore** |
| "等某个线程准备好，别的线程才开始" | **Event** |
| "生产者生产了东西，通知消费者来拿" | **Condition / Queue** |
| "多个线程安全地传递数据" | **Queue** |

这些统称**同步原语（synchronization primitives）**。它们和 `Lock` 一起，构成了多线程协作的工具箱。

### 1.1 核心概念速查
| 原语 | 作用 |
| --- | --- |
| Semaphore | 信号量：限制"同时"能进入的线程数（计数器） |
| Event | 事件：一个线程发信号，其他线程等这个信号 |
| Condition | 条件变量：等待某个条件满足再继续 |
| Queue | 线程安全队列：生产者消费者模式的标配 |

### 1.2 一个关键类比：Semaphore vs Lock
```plain
Lock         = 计数为 1 的 Semaphore（要么进，要么不进）
Semaphore(3) = 计数为 3，最多同时放 3 个线程进去
```

理解了这个类比，你就理解了 Semaphore 的本质：**它就是一个带计数的锁**。

## 二、Semaphore：限流，最多同时 N 个线程
### 2.1 场景描述
数据库连接池通常有上限，比如最多允许 3 个并发连接。超过的请求要排队等待。

```plain
def visit_db(semaphore, name):
    with semaphore:          # 拿到名额才进去, 最多 3 个同时
        print(f"  [{name}] 进入数据库连接池")
        time.sleep(0.5)
        print(f"  [{name}] 离开连接池")

sem = threading.Semaphore(3)
threads = [threading.Thread(target=visit_db, args=(sem, f"T{i}")) for i in range(6)]
```

### 2.2 运行结果
```plain
--- Semaphore(3): 限制最多 3 个线程同时访问 ---
  [T0] 进入数据库连接池
  [T1] 进入数据库连接池
  [T2] 进入数据库连接池
  (0.5 秒后...)
  [T0] 离开连接池
  [T3] 进入数据库连接池
  ...
  (6 个线程分两批, 每次最多 3 个同时)
```

### 2.3 原理
+ `Semaphore(3)` 内部维护一个计数器，初始值为 3
+ 线程执行 `with semaphore:` 时，计数器减 1；为 0 时其他线程阻塞等待
+ 退出 `with` 块时，计数器加 1，唤醒等待的线程
+ 6 个线程，名额只有 3 个 → 分两批执行

### 2.4 补充说明：`semaphore._value`
代码里用了 `semaphore._value` 来显示当前剩余名额。这是**私有属性**，仅用于教学演示，生产代码不要依赖它。实际开发中你不需要知道剩余多少，只需要 `with semaphore:` 即可。

### 2.5 典型用途
+ 数据库连接池限流
+ 爬虫限制并发请求数
+ 限制同时打开的文件数
+ 任何"资源有限、需要排队"的场景

## 三、Event：一个线程发信号，其他线程等
### 3.1 场景描述
主线程要等子线程"初始化完成"才能继续。子线程完成后 `set()`，主线程 `wait()` 直到收到信号。

```plain
def init_system(event):
    print("  初始化线程: 加载配置...")
    time.sleep(2)
    print("  初始化线程: 完成了, 发信号!")
    event.set()                  # 发出信号

def wait_init(event, name):
    print(f"  [{name}] 等待初始化完成...")
    event.wait()                 # 阻塞, 直到 event 被 set
    print(f"  [{name}] 收到信号, 开始干活!")
```

### 3.2 运行结果
```plain
--- Event: 大家都等初始化完成才动 ---
  初始化线程: 加载配置...
  [W0] 等待初始化完成...
  [W1] 等待初始化完成...
  [W2] 等待初始化完成...
  (2 秒后...)
  初始化线程: 完成了, 发信号!
  [W0] 收到信号, 开始干活!
  [W1] 收到信号, 开始干活!
  [W2] 收到信号, 开始干活!
```

### 3.3 三个关键方法
| 方法 | 作用 |
| --- | --- |
| `event.set()` | 把标志设为 True，唤醒所有 `wait()`的线程 |
| `event.wait()` | 阻塞，直到标志为 True（若已是 True 则立即返回） |
| `event.clear()` | 把标志重置为 False（可重复使用） |

**特点**：Event 是**一次性广播**——一旦 `set()`，所有等待的线程都会被唤醒，且之后 `wait()` 都立即返回（直到 `clear()`）。

### 3.4 典型用途
+ 等待初始化完成
+ 优雅停止信号（主线程 `set()`，所有工作线程 `wait()` 到信号后退出）
+ 一次性广播通知

## 四、Condition：条件变量（生产者消费者的底层）
### 4.1 场景描述
一个缓冲区（上限 5），生产者往里放，消费者从里取：

+ 缓冲区**满了** → 生产者要等
+ 缓冲区**空了** → 消费者要等
+ 生产/消费后要**通知对方**

```plain
buffer = []
cond = threading.Condition()

def producer(items):
    for i in range(items):
        with cond:
            while len(buffer) >= 5:      # 满了就等
                cond.wait()
            buffer.append(i)
            print(f"  生产 {i} (库存 {len(buffer)})")
            cond.notify()                # 通知消费者
        time.sleep(0.1)

def consumer(items):
    for _ in range(items):
        with cond:
            while len(buffer) == 0:      # 空了就等
                cond.wait()
            item = buffer.pop(0)
            print(f"  消费 {item} (库存 {len(buffer)})")
            cond.notify()                # 通知生产者
        time.sleep(0.15)
```

### 4.2 三个关键方法
| 方法 | 作用 |
| --- | --- |
| `cond.wait()` | 释放锁并阻塞，直到被 `notify()`唤醒后重新拿锁 |
| `cond.notify()` | 唤醒**一个**等待的线程 |
| `cond.notify_all()` | 唤醒**所有**等待的线程 |

### 4.3 为什么必须用 `while` 而不是 `if`？
```plain
while len(buffer) == 0:      # ✅ 正确
    cond.wait()

if len(buffer) == 0:         # ❌ 错误
    cond.wait()
```

原因：`wait()` 被唤醒后，条件**可能又不满足了**（比如多个消费者同时被唤醒，只有一个抢到数据）。用 `while` 重新检查条件，才能保证安全。这叫**防止虚假唤醒（spurious wakeup）**。

### 4.4 重要提醒
Condition 是最底层、最灵活、也**最容易写错**的原语。实际项目中，能用 Queue 就不要手写 Condition。

---

## 五、Queue：线程安全队列（生产者的推荐实现）
### 5.1 场景描述
同样的问题，用 `queue.Queue` 实现，代码大幅简化：

```plain
q = queue.Queue(maxsize=5)

def queue_producer():
    for i in range(8):
        q.put(i)             # 满了会自动阻塞等待
        print(f"  [生产] 放入 {i}")
        time.sleep(0.1)

def queue_consumer():
    for _ in range(8):
        item = q.get()       # 空了会自动阻塞等待
        print(f"  [消费] 取出 {item}")
        q.task_done()
        time.sleep(0.15)
```

### 5.2 对比 Condition 版本
| 对比项 | Condition 手写 | Queue |
| --- | --- | --- |
| 代码量 | 多（要写 while、waitnotify） | 少（只需 put/get） |
| 出错概率 | 高（忘记 while、notify 写错等） | 低（内部已处理好） |
| 可读性 | 差 | 好 |
| 性能 | 差不多 | 差不多 |

**Queue 内部就是用 Condition（或类似机制）实现的**，只是把细节封装好了。所以它能做到"满了自动阻塞、空了自动阻塞"，你不需要手写任何等待逻辑。

### 5.3 Queue 的常用方法
| 方法 | 作用 |
| --- | --- |
| `q.put(item)` | 放入元素，满了阻塞 |
| `q.put_nowait(item)` | 放入元素，满了抛 `queue.Full` |
| `q.get()` | 取出元素，空了阻塞 |
| `q.get_nowait()` | 取出元素，空了抛 `queue.Empty` |
| `q.task_done()` | 标记一个任务完成（配合 `q.join()`） |
| `q.join()` | 等待所有任务被 `task_done()` 标记 |

### 5.4 三种 Queue
```plain
queue.Queue()        # 先进先出 (FIFO)
queue.LifoQueue()    # 后进先出 (LIFO, 栈)
queue.PriorityQueue()# 优先级队列
```

### 5.5 典型用途
+ 生产者消费者模式（首选）
+ 线程池任务队列
+ 多线程数据传递
+ 任何"多个线程安全共享数据"的场景

## 六、四者对比与选择指南
### 6.1 一张表看懂区别
| 原语 | 解决的问题 | 核心方法 | 典型场景 |
| --- | --- | --- | --- |
| Semaphore | 限流：最多 N 个同时 | `with sem:` | 连接池、限流 |
| Event | 信号通知：等一个标志 | `set()` / `wait()` | 初始化完成、停止信号 |
| Condition | 条件等待：等条件满足 | `wait()`/ `notify()` | 复杂协作（底层） |
| Queue | 线程安全传数据 | `put()`/ `get()` | 生产者消费者 |

### 6.2 经验法则（按优先级）
```plain
1. 传递数据          → 用 Queue（别自己加锁）
2. 简单"等一个信号"   → 用 Event
3. 限制并发数        → 用 Semaphore
4. 只有 Queue/Event/Semaphore 都搞不定 → 才考虑 Condition
```

**核心思想：能用高层封装（Queue）就不用底层原语（Condition）。** 高层封装已经把边界情况处理好了，代码更短、更安全。

## 七、总结
### 7.1 概念回顾
+ **Semaphore** = 限流，最多 N 个同时（连接池、限流器）
+ **Event** = 信号通知，等某个标志（初始化完成、停止信号）
+ **Condition** = 条件等待，复杂协作的底层
+ **Queue** = 线程安全队列，生产者消费者首选（内部自带锁）

### 7.2 常见误区提醒
| 误区 | 纠正 |
| --- | --- |
| "Condition 的 `wait()`外面用 `if`判断就行" | 必须用 `while`，防止虚假唤醒 |
| "手写 Condition 比 Queue 更专业" | 恰恰相反，Queue 是封装好的最佳实践 |
| "Semaphore 和 Lock 完全一样" | Lock 是 Semaphore(1) 的特例，Semaphore 可限流 |
| "Event 可以反复用" | `set()`后需 `clear()`才能复用，否则一直处于已触发状态 |
| "Queue 满了会报错" | 默认 `put()`会阻塞等待，`put_nowait()`才报错 |

# 05 线程池
## 一、为什么需要线程池？
### 1.1 手动创建线程的问题
前面章节每次都写 `Thread(...).start()`，看起来简单，但真实项目里会暴露三个问题：

| 问题 | 说明 |
| --- | --- |
| **创建/销毁有开销** | 每个请求都开一个新线程，线程的创建和销毁本身就要消耗时间和内存 |
| **数量不可控** | 1000 个任务 = 1000 个线程 → 内存爆炸、上下文切换频繁、性能反而下降 |
| **管理啰嗦** | 得手动 `join`、手动收集结果，代码冗长易错 |

### 1.2 线程池的思路
**预先创建固定数量的线程，任务来了排队丢进去。**

线程池 = 一个"池子"里养着 N 个线程，任务被放进队列，池子里的线程轮流取任务执行。带来的好处：

+ **线程复用**：线程不销毁，一直干活，省掉创建/销毁开销
+ **数量可控**：池子大小固定，不会因为任务多就把系统压垮
+ **结果自动收集**：提交任务返回 `Future`，结果直接从 `Future` 里取

### 1.3 核心概念速查
| 概念 | 解释 |
| --- | --- |
| `ThreadPoolExecutor` | 线程池对象 |
| `max_workers` | 池子里最多几个线程 |
| `executor.submit(fn, ...)` | 提交任务，返回 `Future` |
| `Future.result()` | 取任务结果（阻塞直到完成） |
| `executor.map(fn, iter)` | 批量提交，返回结果的迭代器（**保序**） |
| `as_completed(futures)` | 谁先完成先返回谁（**不保序**） |
| `with ThreadPoolExecutor(...)` | 退出时自动 shutdown，等所有任务完成 |

### 1.4 submit vs map
```plain
submit: 逐个提交，灵活（可以传不同参数，逐个取结果）
map:    批量提交一个可迭代对象，结果按输入顺序排列
```

### 1.5 重要认知
**线程池是"日常并发任务的第一选择"。绝大多数场景不需要手动 Thread。**
但它仍然受 GIL 限制 → **只适合 I/O 密集**（见 01 章）。

## 二、案例 1：基础用法——submit + result
### 2.1 场景描述
提交任务，用 `Future.result()` 取结果。

```plain
def fetch(url):
    delay = {"a": 1, "b": 2, "c": 3, "d": 1}[url]
    time.sleep(delay)
    return f"{url} 的响应 (耗时 {delay}s)"

with ThreadPoolExecutor(max_workers=3) as pool:
    future1 = pool.submit(fetch, "a")
    future2 = pool.submit(fetch, "b")
    print(f"  {future1.result()}")
    print(f"  {future2.result()}")
```

### 2.2 运行结果
```plain
--- submit: 提交任务, result 取结果 ---
  a 的响应 (耗时 1s)
  b 的响应 (耗时 2s)
```

### 2.3 三个要点
1. `**submit(fn, *args)**`** 立即返回**：提交后不等任务完成，马上拿到一个 `Future` 对象
2. `**future.result()**`** 才阻塞**：调用 `result()` 时才等任务完成并取回返回值
3. `**with**`** 自动管理**：退出 `with` 块时自动 `shutdown()`，等待所有任务结束

**理解 Future**：可以把它当成"未来才会有结果的凭据"。提交任务时先给你一张凭据，需要用结果时拿凭据去兑换（`result()`）。

## 三、案例 2：map——批量提交，结果保序
### 3.1 场景描述
一批相似的任务，用 `map` 一行搞定，且结果**按输入顺序**返回。

```plain
start = time.perf_counter()
with ThreadPoolExecutor(max_workers=3) as pool:
    results = pool.map(fetch, ["a", "b", "c", "d"])
    for r in results:
        print(f"  {r}")
print(f"  总耗时: {time.perf_counter() - start:.2f}s")
```

### 3.2 运行结果
```plain
--- map: 批量提交, 按输入顺序返回 ---
  a 的响应 (耗时 1s)
  b 的响应 (耗时 2s)
  c 的响应 (耗时 3s)
  d 的响应 (耗时 1s)
  总耗时: 4.00s  (并发执行, 不是 1+2+3+1=7s)
```

### 3.3 关键理解：耗时 4s 怎么来的？
4 个任务耗时分别是 1、2、3、1 秒，总共 7 秒。3 个线程并发执行：

```plain
时间轴:
  线程1: [a:1s] [c:3s]        → 完成于 4s
  线程2: [b:2s] [d:1s]        → 完成于 3s
  线程3: (空闲)
```

+ 前三个任务 a、b、c 同时开始
+ a 1 秒后完成 → 该线程接着执行 d（1 秒）
+ 最慢的是 c，耗时 3 秒；它所在的线程到 3 秒完成，此时 d 也刚好完成（2s 开始 + 1s = 3s 左右，实际因调度可能到 4s）
+ **总耗时约等于最长的一批任务时间，而非总和**

### 3.4 保序是什么意思？
`map` 返回的结果**按输入列表的顺序**排列，即使 `c`（耗时 3s）最晚完成，结果里 `c` 仍然排第三位。

对比：`as_completed` 是**不保序**的，谁先完成先返回谁。

---

## 四、案例 3：as_completed——谁先完成先处理谁
### 4.1 场景描述
有时我们不关心顺序，只想"哪个任务先好，先处理哪个"。

```plain
with ThreadPoolExecutor(max_workers=3) as pool:
    futures = {pool.submit(fetch, url): url for url in ["a", "b", "c"]}
    for future in as_completed(futures):
        url = futures[future]
        print(f"  {url} 先完成: {future.result()}")
```

### 4.2 运行结果
```plain
--- as_completed: 不保序, 谁先完成先返回 ---
  a 先完成: a 的响应 (耗时 1s)
  b 先完成: b 的响应 (耗时 2s)
  c 先完成: c 的响应 (耗时 3s)
```

### 4.3 原理
`as_completed(futures)` 返回一个**迭代器**，每次 `next` 时**阻塞**，直到有一个任务完成，就返回那个 `Future`。所以遍历顺序 = 任务完成顺序。

### 4.4 典型用途
+ 并发请求多个接口，谁先返回先渲染
+ 超时控制：给每个任务设时限，先用先得
+ 用户希望"快速看到部分结果"的场景

---

## 五、案例 4：实战——并发下载（I/O 密集）
### 5.1 场景描述
下载 20 个页面，每个耗时 0.3 秒（模拟网络延迟）。

```plain
def download(page):
    time.sleep(0.3)
    return f"页面 {page} 的内容"

pages = list(range(20))
start = time.perf_counter()
with ThreadPoolExecutor(max_workers=5) as pool:
    results = list(pool.map(download, pages))
print(f"  总耗时: {time.perf_counter() - start:.2f}s")
```

### 5.2 运行结果
```plain
--- 实战: 并发下载 20 个页面 ---
  下载了 20 个页面
  总耗时: 1.20s
  (20 × 0.3s = 6s 串行, 现在 5 线程并发约 1.2s)
```

### 5.3 为什么是 1.2s？
+ 20 个任务，5 个线程，分成 4 批
+ 每批 0.3s → 4 × 0.3 = 1.2s
+ 相比串行的 6s，快了 5 倍

**这就是 I/O 密集任务并发的意义**：`time.sleep`（或真实网络请求）期间线程阻塞，GIL 被释放，其他线程可以继续跑。所以 I/O 密集场景下多线程能真正提速。

---

## 六、案例 5：异常处理——任务出错怎么办
### 6.1 场景描述
任务内部抛异常，线程池会怎么处理？

```plain
def risky(n):
    if n == 2:
        raise ValueError(f"任务 {n} 出错了")
    return n * 10

with ThreadPoolExecutor(max_workers=3) as pool:
    futures = [pool.submit(risky, i) for i in range(4)]
    for i, f in enumerate(futures):
        try:
            print(f"  任务 {i}: {f.result()}")
        except ValueError as e:
            print(f"  任务 {i}: 捕获异常 -> {e}")
```

### 6.2 运行结果
```plain
--- 异常处理 ---
  任务 0: 0
  任务 1: 10
  任务 2: 捕获异常 -> 任务 2 出错了
  任务 3: 30
```

### 6.3 关键机制
+ 任务抛出的异常**不会让线程池崩溃**，也不会打断程序
+ 异常被**存进 **`**Future**`** 对象**
+ 当你调用 `future.result()` 时，异常被**重新抛出**——所以在 `result()` 处 `try/except` 即可捕获

**注意**：如果你从不调用 `future.result()`，异常会被默默忽略（可能埋下隐患）。用 `map` 时也一样，异常会在迭代到该结果时抛出。

## 七、使用准则与常见误区
### 7.1 max_workers 怎么设？
| 任务类型 | 建议 max_workers | 原因 |
| --- | --- | --- |
| **I/O 密集** | 可以设大点（几十） | 线程大部分时间在等 I/O，GIL 被释放，线程多能提高吞吐 |
| **CPU 密集** | 设成 CPU 核心数 | 受 GIL 限制，多线程无法并行计算，且线程切换反而增加开销 |

**CPU 密集请用进程池**（见 08 章 `ProcessPoolExecutor`），多进程才能绕过 GIL 真正并行。

### 7.2 常见误区
| 误区 | 纠正 |
| --- | --- |
| "线程池能加速 CPU 密集任务" | 受 GIL 限制，CPU 密集用线程池不会提速，反而可能更慢 |
| "`submit` 后马上能拿到结果" | `submit` 立即返回 Future，`result()`才阻塞取结果 |
| "`map` 结果顺序和完成顺序一致" | `map`**保序**（按输入顺序），`as_completed` 才按完成顺序 |
| "任务抛异常会中断整个池" | 异常存进 Future，在 `result()`时抛出，其他任务不受影响 |
| "`max_workers` 越大越好" | 太大导致线程切换开销、内存占用；要按任务类型和机器配置来 |

## 八、总结
### 8.1 核心 API 回顾
| API | 作用 |
| --- | --- |
| `ThreadPoolExecutor(max_workers=N)` | 创建含 N 个线程的池 |
| `submit(fn, *args)` | 提交任务，返回 `Future` |
| `future.result()` | 阻塞取结果 |
| `map(fn, iterable)` | 批量提交，结果保序 |
| `as_completed(futures)` | 按完成顺序返回 |
| `with ...` | 自动等待所有任务完成并关闭池 |

### 8.2 三句话记住线程池
1. **线程池 = 预先造好固定数量线程，任务排队复用它们**
2. **I/O 密集用线程池（并发有效），CPU 密集用进程池（绕过 GIL）**
3. **能用线程池就别手写 Thread（复用线程、代码简洁、自动收集结果）**

# 06 多进程
## 一、为什么需要多进程？
### 1.1 回顾：多线程的局限
第 01 章已经演示过：**多线程受 GIL 限制，跑 CPU 密集任务不但不快，反而更慢**。原因是 GIL 保证同一时刻只有一个线程执行 Python 字节码，多线程在 CPU 密集场景下用不上多核。

### 1.2 进程 vs 线程
| 维度 | 线程 | 进程 |
| --- | --- | --- |
| 本质 | 同一进程内的多条执行流 | 独立的内存空间 + 独立Python 解释器 + 独立的 GIL |
| 内存 | 共享 | 不共享 |
| GIL | 共用一把 GIL | **每个进程有自己的 GIL** |
| CPU 并行 | ❌ 受 GIL 限制 | ✅ 真并行 |
| 开销 | 轻 | 重（创建/销毁要复制解释器） |
| 通信 | 直接共享变量 | 麻烦，要用 Queue/Pipe |

**核心认知**：多进程能真正并行跑 CPU 任务，因为每个进程有独立的 GIL，互不干扰。

### 1.3 代价：进程比线程"重"
+ **创建/销毁开销大**：要复制一份解释器
+ **内存不共享**：进程间通信麻烦（下一章讲）
+ **数量受限**：进程数别超过 CPU 核心数，开多了只会频繁切换反而更慢

### 1.4 核心概念速查
| 概念 | 解释 |
| --- | --- |
| `Process(target=fn)` | 创建进程 |
| `.start()` | 启动进程 |
| `.join()` | 等进程结束 |
| `cpu_count()` | 查 CPU 核心数 |
| `if __name__ == ...` | **Windows 上必须！** 否则无限递归创建进程 |

## 二、两个硬约束

### 2.1 约束一：必须 `if __name__ == "__main__":`
**原因**：Windows 用 **spawn** 方式启动子进程——子进程会**重新 import 你的脚本**。如果创建进程的代码在模块顶层，子进程 import 时又再创建进程 → **无限递归**。

```plain
# ✅ 正确：创建进程的代码放在 __main__ 里
if __name__ == "__main__":
    p = Process(target=cpu_bound, args=(N,))
    p.start()
    p.join()
```

```plain
# ❌ 错误：模块顶层直接创建进程 → Windows 上无限递归
p = Process(target=cpu_bound, args=(N,))
p.start()
p.join()
```

Linux/macOS 默认用 **fork** 方式（复制父进程），不会重新 import，所以不写 `__main__` 保护也能跑。但为了跨平台可移植，**永远要写**。

#### Windows 的 spawn 机制
Windows 没有 Linux 的 `fork`（直接复制父进程内存），只能用 **spawn**：**启动一个全新的 Python 解释器进程，从头 import 你的脚本**。

```plain
主进程启动
  └─ 运行 my_script.py
       ├─ import 各种库
       ├─ 定义函数
       └─ 执行顶层语句

创建子进程时（spawn）：
  └─ 启动一个全新的 Python 解释器
       └─ 【重新 import my_script.py】← 关键在这里！
            ├─ import 各种库
            ├─ 定义函数
            └─ 执行顶层语句  ← 如果顶层有 p.start()，就又创建子进程！
```

**spawn 不是"复制"父进程，而是"重新运行一遍你的脚本文件"**（只是不执行 `__main__` 块）。所以子进程启动时，会把你脚本的**模块顶层代码再执行一次**。

```python
# my_script.py
from multiprocessing import Process

def work():
    print("干活")

p = Process(target=work)   # 顶层语句
p.start()                  # 顶层语句
p.join()                   # 顶层语句
```

```python
【没有 __main__ 保护】
主进程 python my_script.py
  __name__ = "__main__"
  └─ 执行顶层 p.start()
       └─ 子进程 spawn
            └─ 重新 import my_script.py
                 __name__ = "my_script"（但代码没保护，照样执行 p.start()）
                 └─ 又创建进程 → 无限递归 💥

【有 __main__ 保护】
主进程 python my_script.py
  __name__ = "__main__"
  └─ if __name__ == "__main__": 成立 → p.start()
       └─ 子进程 spawn
            └─ 重新 import my_script.py
                 __name__ = "my_script"
                 └─ if __name__ == "__main__": 不成立 → 跳过 ✅
                 └─ 只登记函数定义，不创建进程 → 递归终止
```

### 2.2 约束二：进程 target 必须是"模块顶层函数"
模块顶层：

一个 `.py` 文件就像一栋楼：

```plain
┌─────────────────────────────────────┐
│  模块顶层（楼的一楼大厅）              │
│  - import 语句                        │
│  - 全局变量                            │
│  - def 函数定义（只是"登记"，不执行）  │
│  - class 定义                          │
│  - 直接写的代码（会立即执行！）        │
│                                       │
│  ┌─────────────────────────────────┐  │
│  │ 函数内部（楼上的房间）            │  │
│  │ - 只有被调用时才进去执行          │  │
│  └─────────────────────────────────┘  │
└─────────────────────────────────────┘
```

**"模块顶层"就是：没有缩进、直接写在文件里的代码。** 不在任何函数、类、`if` 块里面的那些行。

例如：

```python
# ========== 以下都是"模块顶层"（没有缩进）==========

import time                          # 顶层
from multiprocessing import Process  # 顶层

N = 30_000_000                       # 顶层：全局变量，import 时就会执行

def cpu_bound(n):                    # 顶层：函数"定义"（登记名字，不执行函数体）
    total = 0
    for i in range(n):
        total += i
    return total

p = Process(target=cpu_bound)        # 顶层：这行是"直接执行的代码"！
p.start()                            # 顶层：import 时就会执行！
p.join()                             # 顶层：import 时就会执行！

# ========== 以下是函数内部（有缩进）==========

def demo():
    x = 1                            # 函数内部，只有 demo() 被调用才执行
    print(x)
```

**原因**：spawn 需要把目标函数 **pickle 序列化**传给子进程，而**嵌套函数 / lambda 无法被 pickle**，会报错：`Can't get local object`。

```plain
# ✅ 正确：函数定义在模块顶层
def cpu_bound(n):
    total = 0
    for i in range(n):
        total += i
    return total

if __name__ == "__main__":
    p = Process(target=cpu_bound, args=(N,))
```

python

```plain
# ❌ 错误：函数嵌套在 demo 函数里
def demo_parallel():
    def cpu_bound(n):        # 嵌套函数, 无法 pickle
        ...
    p = Process(target=cpu_bound, args=(N,))   # 报错！
```

**这就是为什么本文件所有进程入口函数都放在模块顶层，不能塞进 demo 函数里。**

## 三、案例 1：多进程真的能并行（对比实验）
### 3.1 场景描述
跑 2 次 CPU 密集计算（各 3000 万次累加），对比"单进程串行"和"2 进程并行"的耗时。

```plain
N = 30_000_000

# 单进程跑 2 次
start = time.perf_counter()
cpu_bound(N)
cpu_bound(N)
single = time.perf_counter() - start

# 2 进程并行跑
start = time.perf_counter()
p1 = Process(target=cpu_bound, args=(N,))
p2 = Process(target=cpu_bound, args=(N,))
p1.start()
p2.start()
p1.join()
p2.join()
multi = time.perf_counter() - start
```

### 3.2 运行结果（4 核机器示例）
```plain
CPU 核心数: 4

  单进程跑 2 次:   2.400s
  2 进程并行跑:     1.250s   ← 接近单次的时间!

  结论: 多进程把 2 次计算的时间从 2.400s 压到 1.250s
  (多线程做不到这一点, 因为 GIL)
```

### 3.3 为什么多进程能提速？
+ 两个进程各有一个**独立的 GIL**，各占一个 CPU 核心
+ 真正同时执行，耗时 ≈ 单次计算时间
+ 多线程做同样的事：两个线程抢一把 GIL，轮流跑，耗时 ≈ 2 次之和，甚至更慢

### 3.4 实践提示
+ `cpu_count()` 查核心数，进程数**别超过核心数**
+ 4 核机器跑 4 个 CPU 密集进程刚好；跑 8 个只会频繁切换，反而慢

## 四、案例 2：进程不共享变量（和线程的关键区别）
### 4.1 场景描述
子进程里修改全局变量，看主进程能不能看到。

```plain
shared_value = 0   # 全局变量

def modify_global():
    global shared_value
    shared_value = 999
    print(f"  子进程里改成了: {shared_value}")

# 主进程
shared_value = 0
p = Process(target=modify_global)
p.start()
p.join()
print(f"  主进程里还是: {shared_value}")
```

### 4.2 运行结果
```plain
--- 进程不共享内存 ---
  子进程里改成了: 999
  主进程里还是: 0  ← 没被改!
  (每个进程有独立的内存空间, 改的是子进程自己的副本)
```

### 4.3 关键理解
+ 子进程启动时，**复制**了父进程的内存（写时复制）
+ 子进程改的是**自己的副本**，父进程完全看不到
+ **这和线程完全不同**：线程共享同一份内存，改了就都看得到

**对比第 03 章**：线程里共享变量要加锁防竞态；进程里根本不存在"共享变量"这个问题，因为内存天然隔离。但代价是——**想传数据就必须显式通信**。

## 五、案例 3：获取子进程返回值（Queue 传回结果）
### 5.1 场景描述
进程不共享内存，那怎么把子进程的计算结果传回主进程？用 `multiprocessing.Queue`。

```plain
def compute_square(n, result_queue):
    result_queue.put(n * n)

q = Queue()
p = Process(target=compute_square, args=(12, q))
p.start()
p.join()
print(f"  12² = {q.get()}")
```

### 5.2 运行结果
```plain
--- 进程返回值 (用 Queue 传回) ---
  12² = 144
```

### 5.3 原理
+ `multiprocessing.Queue` 是**跨进程**的队列，底层通过管道 + 序列化实现
+ 子进程 `put()` 结果，主进程 `get()` 取出
+ `p.join()` 保证子进程写完后再取，避免空等

**注意**：这里的 `Queue` 是 `multiprocessing.Queue`，不是第 04 章的 `queue.Queue`。前者跨进程，后者只在单进程内多线程用。**别混用**。

## 六、使用准则与常见误区
### 6.1 什么时候用进程，什么时候用线程？
| 任务类型 | 用什么 | 原因 |
| --- | --- | --- |
| **CPU 密集** | 进程 / 进程池 | 每个进程独立 GIL，能用满多核 |
| **I/O 密集** | 线程池 / 协程 | 进程太重，不划算；I/O 时 GIL 会释放 |

### 6.2 常见误区
| 误区 | 纠正 |
| --- | --- |
| "Windows 上不写 `__main__` 也能跑" | Linux 能跑是 fork 的运气，Windows 必崩，永远写 `__main__` |
| "进程 target 可以是 lambda 或嵌套函数" | spawn 要 pickle，嵌套函数/lambda 无法 pickle，必须模块顶层函数 |
| "进程之间改全局变量能生效" | 进程内存隔离，改的是副本，主进程看不到 |
| "进程数越多越快" | 超过 CPU 核心数只会频繁切换，反而慢 |
| "`multiprocessing.Queue`和 `queue.Queue`一样" | 前者跨进程，后者只限单进程内多线程，别混用 |

## 七、总结
### 7.1 核心要点
+ `Process(target=fn)` → 创建进程
+ **多进程 = 真并行**，因为每个进程独立 GIL
+ **进程不共享内存** → 要通信得用 `Queue`/`Pipe`
+ 进程比线程"重"，创建开销大、数量受限

### 7.2 三句话记住多进程
1. **CPU 密集用进程（独立 GIL 真并行），I/O 密集用线程（进程太重不划算）**
2. **进程数别超过 CPU 核心数**
3. **Windows 上：进程创建放 **`**__main__**`** 里，target 用模块顶层函数**

### 7.3 与线程的对照记忆
```plain
线程：共享内存 + 共用 GIL → 轻量，适合 I/O 密集，要防竞态
进程：独立内存 + 独立 GIL → 重量，适合 CPU 密集，要显式通信
```

# 07 进程间通信 Queue/Pipe/Manager
## 一、为什么进程之间需要"显式通信"？
### 1.1 进程内存隔离
**进程不共享内存**，子进程改全局变量，主进程看不到（改的是子进程自己的副本）。所以进程之间要协作、传数据，**必须用专门的通信机制**。

### 1.2 线程 vs 进程的通信对比
| 维度 | 通信方式 | 注意事项 |
| --- | --- | --- |
| **线程** | 共享内存，直接读写变量 | 要加锁防竞态（第 03 章） |
| **进程** | 内存隔离，必须用专门机制 | 要序列化、有通信开销 |

一句话：**线程通信"免费但危险"（要加锁），进程通信"安全但费力"（要显式传）。**

### 1.3 核心概念速查
| 机制 | 说明 |
| --- | --- |
| **Queue** | 进程安全队列，生产者消费者模式（**最常用**） |
| **Pipe** | 双向管道，两端直接收发（一对一，快） |
| **Manager** | 共享 dict/list，多进程读写同一份数据 |
| **Value/Array** | 共享内存，底层快但原始（C 类型） |

### 1.4 选型速记
```plain
传任务/结果          → Queue（最常用）
一对一收发           → Pipe（比 Queue 快一点）
共享一份可变数据      → Manager（dict/list，方便但有性能开销）
```

### 1.5 重要前提：target 必须是模块顶层函数
Windows 的 spawn 需要 **pickle 序列化**目标函数传给子进程，嵌套函数/lambda 无法 pickle（报错 `Can't get local object`）。**所以本文件所有进程入口函数都放在模块顶层。**

---

## 二、案例 1：Queue——进程安全队列（最常用）
### 2.1 场景描述
一个进程生产数据，另一个进程消费数据。这是进程间通信最典型的模式。

```python
def producer(q,n):
    for i in range(n):
        q.put(i)
        print(f"  [生产] 放入 {i}")

def consumer(q, n):
    for _ in range(n):
        item = q.get()
        print(f"  [消费] 取出 {item}")

q = Queue()
p1 = Process(target=producer, args=(q, 5))
p2 = Process(target=consumer, args=(q, 5))
p1.start()
p2.start()
p1.join()
p2.join()
```

### 2.2 运行结果
```plain
--- Queue: 进程间生产者消费者 ---
  [生产] 放入 0
  [消费] 取出 0
  [生产] 放入 1
  [消费] 取出 1
  ...
```

（具体交错顺序取决于调度，但 5 个元素都会被正确传递）

### 2.3 关键理解
1. `**multiprocessing.Queue**`** 是跨进程的**：底层通过管道 + 序列化实现，数据被 pickle 后传给另一进程
2. `**q.get()**`** 会阻塞**：队列空时消费者等待，直到有数据
3. `**q.put()**`** 默认不阻塞**（除非设了 `maxsize` 且满了）
4. **和 **`**queue.Queue**`** 的区别**：`queue.Queue` 只能在同一进程内的多线程间用；`multiprocessing.Queue` 才能跨进程。**别混用**

**对比第 04 章**：线程版的 Queue 是 `queue.Queue`，进程版是 `multiprocessing.Queue`。用法几乎一样（`put`/`get`），但作用域不同。

### 2.4 典型用途
+ 进程池的任务分发（第 08 章 `ProcessPoolExecutor` 内部就用它）
+ 生产者消费者模式
+ 多进程数据收集

---

## 三、案例 2：Pipe——双向管道（一对一）
### 3.1 场景描述
两个进程点对点通信，用 `Pipe()` 拿一对连接对象，一端发、一端收。

```python
def pipe_sender(conn):
    conn.send("你好, 这是通过管道发来的消息")
    conn.send([1, 2, 3])
    conn.close()

parent_conn, child_conn = Pipe()
p = Process(target=pipe_sender, args=(child_conn,))
p.start()
print(f"  收到: {parent_conn.recv()}")
print(f"  收到: {parent_conn.recv()}")
p.join()
```

### 3.2 运行结果
```plain
--- Pipe: 双向管道 ---
  收到: 你好, 这是通过管道发来的消息
  收到: [1, 2, 3]
```

### 3.3 三个关键点
| 方法 | 作用 |
| --- | --- |
| `Pipe()` | 返回一对 `(conn1, conn2)`，**双向** |
| `conn.send(obj)` | 发送任意可 pickle 的对象 |
| `conn.recv()` | 接收，**阻塞**直到有数据 |
| `conn.close()` | 关闭连接（好习惯） |

**特点**：

+ **一对一**：一对 Pipe 只有两端，不适合多个进程共享
+ **比 Queue 快**：底层更轻量，少一层队列管理
+ **双向**：两端都能 send/recv（不是单向的）

### 3.4 注意事项
+ 多个进程同时用同一对 Pipe 会出问题（**不是进程安全的**），多进程通信用 Queue
+ 发送方 `close()` 后，接收方 `recv()` 会抛 `EOFError`，可用来判断"发完了"
+ 大数据量时注意管道缓冲区限制，可能导致死锁（收发要配合好）

## 四、案例 3：Manager——共享 dict / list
### 4.1 场景描述
多个进程要**共享同一份可变数据**（比如一个字典），用 `Manager()` 创建代理对象。

```python
def add_to_dict(shared_dict, key, value):
    shared_dict[key] = value

with Manager() as manager:
    shared = manager.dict()

    procs = [
        Process(target=add_to_dict, args=(shared, "a", 1)),
        Process(target=add_to_dict, args=(shared, "b", 2)),
        Process(target=add_to_dict, args=(shared, "c", 3)),
    ]
    for p in procs:
        p.start()
    for p in procs:
        p.join()

    print(f"  主进程读到的字典: {dict(shared)}")
```

### 4.2 运行结果
```plain
--- Manager: 多进程共享一个字典 ---
  主进程读到的字典: {'a': 1, 'b': 2, 'c': 3}  ← 三个子进程的写入都看到了
```

### 4.3 原理：Manager 是"代理"
`manager.dict()` 返回的**不是真正的 dict**，而是一个**代理对象**：

```plain
子进程 A ──┐
子进程 B ──┼──→ 代理对象 ──→ Manager 服务进程 ──→ 真正的 dict
子进程 C ──┘
```

+ 真正的数据存在一个**独立的 Manager 服务进程**里
+ 各个子进程拿到的是代理，操作代理时会通过**IPC（进程间通信）**转发给服务进程
+ 所以**能看到彼此的写入**，实现"共享"

### 4.4 代价：性能差
因为每次读写都要走 IPC 序列化，**Manager 比直接操作本地变量慢得多**（可能慢几十倍）。

**使用原则**：能不用 Manager 就不用。只在"多个进程必须共享一份可变状态"时才用。

### 4.5 Manager 支持的类型
```plain
manager.dict()      # 共享字典
manager.list()      # 共享列表
manager.Value()     # 共享单值
manager.Queue()     # 共享队列（等价于 multiprocessing.Queue）
manager.Lock()      # 共享锁
```

## 五、四者对比与选型指南
### 5.1 一张表看懂
| 机制 | 适用场景 | 方向 | 性能 | 复杂度 |
| --- | --- | --- | --- | --- |
| **Queue** | 生产者消费者、传任务/结果 | 单向（可多对多） | 中 | 低 |
| **Pipe** | 两个进程点对点 | 双向 | 高（最快） | 低 |
| **Manager** | 多进程共享 dict/list | 共享 | 低（慢） | 中 |
| **Value/Array** | 共享简单 C 类型 | 共享 | 高 | 高（原始） |

### 5.2 选型决策树
```plain
需要传数据吗？
├─ 是 → 是"任务/结果"这种流式传递吗？
│        ├─ 是 → Queue（最常用）
│        └─ 否，只有两个进程 → Pipe（更快）
└─ 需要共享一份可变状态（dict/list）吗？
         ├─ 是 → Manager（能不用就不用，性能差）
         └─ 只是简单数值 → Value/Array（底层快，但要查文档）
```

### 5.3 使用准则
+ **生产者消费者 → Queue**
+ **两个进程点对点 → Pipe**
+ **多个进程共享一份可变状态 → Manager**（能不用尽量不用，性能差）
+ **通信数据结构尽量简单**（能传基本类型就别传大对象，要序列化，大对象开销大）

## 六、常见误区与注意事项
| 误区 | 纠正 |
| --- | --- |
| "`multiprocessing.Queue`和 `queue.Queue`一样" | 前者跨进程，后者只限单进程内多线程，别混用 |
| "Pipe 可以多个进程共用" | Pipe 是**一对一**，多进程共用会乱，多进程Queue |
| "Manager 很方便，随便用" | Manager 走 IPC 代理，**性能很差**，能不用就不用 |
| "进程间传大对象没关系" | 所有数据都要 pickle 序列化，大对象开销巨大，尽量传小数据 |
| "Queue 的 `get()`不会阻塞" | 队列空时 `get()`**会阻塞**，直到有数据 |
| "Pipe 发完不用 close" | 不 close 可能导致接收方一直阻塞或资源泄漏，好习惯要 close |

## 七、总结
### 7.1 核心要点
+ **进程内存隔离 → 通信必须显式**
+ **Queue** = 进程安全队列，传任务/结果首选
+ **Pipe** = 一对一双向管道，比 Queue 快
+ **Manager** = 共享 dict/list，方便但有开销
+ **Value/Array** = 底层共享内存，需要时再查文档

### 7.2 三句话记住进程通信
1. **传数据用 Queue（最常用），点对点用 Pipe（最快），共享状态用 Manager（最慢但方便）**
2. **所有通信数据都要 pickle 序列化，尽量传小数据**
3. **线程用 **`**queue.Queue**`**，进程用 **`**multiprocessing.Queue**`**，别混用**

### 7.3 与线程通信的对照
```plain
线程通信：共享内存 + 加锁（第 03 章 Lock）
进程通信：内存隔离 + 显式传（本章 Queue/Pipe/Manager）
```

# 08 进程池
## 一、为什么需要进程池？
### 1.1 手动开进程的问题
和第 05 章手动开线程一样，手动 `Process` 也有三个痛点：

| 问题 | 说明 |
| --- | --- |
| **创建开销大** | 每个任务开一个进程，而进程创建要复制解释器，比线程重得多 |
| **数量失控** | 100 个任务 = 100 个进程，远超核心数 → 频繁切换，反而更慢 |
| **结果收集麻烦** | 得手动 join、手动用 Queue 收结果 |

### .2 进程池的思路
**预先创建固定数量的进程（通常 = CPU 核心数），任务排队执行。**

好处：

+ **进程复用**：省掉创建/销毁开销
+ **数量可控**：默认就是 CPU 核心数，正好吃满多核
+ **结果自动收集**：和线程池一样，`Future` / `map` 直接用

### 1.3 和线程池的关系：API 几乎一模一样
第 05 章的线程池代码，**只需把 **`**ThreadPoolExecutor**`** 换成 **`**ProcessPoolExecutor**`，其余写法完全不变：

```python
# 线程池
with ThreadPoolExecutor(max_workers=4) as pool:
    results = list(pool.map(fn, data))

# 进程池（只改类名！）
with ProcessPoolExecutor(max_workers=4) as pool:
    results = list(pool.map(fn, data))
```

`map` / `submit` / `as_completed` / `Future.result()` 全部通用。这是 `concurrent.futures` 设计的精髓：**统一接口，切换执行器即可**。

### 1.4 核心概念速查
| 概念 | 说明 |
| --- | --- |
| `ProcessPoolExecutor` | 进程池，适合 CPU 密集 |
| `max_workers` | 进程数（默认 = CPU 核心数） |
| `map`/ `submit` | 和线程池用法完全一致 |

| 概念 | 解释 |
| --- | --- |
| `ProcessPoolExecutor` | 进程池对象 |
| `max_workers` | 池子里最多几个线程 |
| `executor.submit(fn, ...)` | 提交任务，返回 `Future` |
| `Future.result()` | 取任务结果（阻塞直到完成） |
| `executor.map(fn, iter)` | 批量提交，返回结果的迭代器（**保序**） |
| `as_completed(futures)` | 谁先完成先返回谁（**不保序**） |
| `with ProcessPoolExecutor(...)` | 退出时自动 shutdown，等所有任务完成 |

### 1.5 一句话区分线程池 vs 进程池
```plain
ThreadPoolExecutor   → I/O 密集（等网络/磁盘）
ProcessPoolExecutor  → CPU 密集（算数/图像/加密）
```

## 二、重要提醒：进程池的两个硬约束
这是和线程池**唯一实质性的区别**，必须重点讲。

### 2.1 约束一：传入的函数必须是"模块顶层函数"
**原因**：进程池要把函数 **pickle 序列化**后传给子进程，而以下对象无法 pickle：

```python
# ❌ lambda：无法 pickle
pool.map(lambda x: x * 2, data)

# ❌ 嵌套函数：无法 pickle（报错 Can't get local object）
def outer():
    def inner(x):
        return x * 2
    pool.map(inner, data)

# ❌ 类方法（绑定到实例的方法）：序列化会失败
pool.map(obj.method, data)

# ✅ 模块顶层函数：可以 pickle
def double(x):
    return x * 2
pool.map(double, data)
```

**对比线程池**：线程池没有这个限制，因为它不需要序列化函数（线程共享内存）。这是进程池特有的坑。

### 2.2 约束二：Windows 上要放 `if __name__ == "__main__":` 里
和第 06 章一样，Windows 用 spawn 启动子进程会重新 import 脚本，创建进程池的代码裸露在顶层会导致无限递归。

```python
# ✅ 正确
if __name__ == "__main__":
    with ProcessPoolExecutor() as pool:
        ...
```

本文件里所有 `demo_*` 函数都在 `__main__` 块里被调用，所以安全。但如果你自己写脚本，记得加保护

## 三、案例 1：进程池基础——map 做 CPU 密集计算
### 3.1 场景描述
并行判断 6 个大数是不是质数（纯 CPU 计算）。

```plain
def is_prime(n):
    if n < 2:
        return False
    for i in range(2, int(n ** 0.5) + 1):
        if n % i == 0:
            return False
    return True

numbers = [1_000_003, 1_000_007, 1_000_019, 999_983, 999_979, 999_961]

start = time.perf_counter()
with ProcessPoolExecutor() as pool:   # 默认进程数 = CPU 核心数
    results = list(pool.map(is_prime, numbers))
print(f"  耗时: {time.perf_counter() - start:.3f}s")
```

### 3.2 运行结果（4 核示例）
```plain
--- ProcessPoolExecutor: 并行判断质数 ---
  结果: {1000003: True, 1000007: True, 1000019: True, ...}
  耗时: 0.180s
  (进程池按 CPU 核心数并行, 比串行快)
```

### 3.3 关键点
+ `**ProcessPoolExecutor()**`** 不传 **`**max_workers**`** 时默认 = **`**os.cpu_count()**`，正好吃满多核
+ `map` 结果**保序**（和线程池一样）
+ 每个质数判断是一个纯计算任务，没有 I/O，所以进程池加速明显

## 四、案例 2：submit + result（和线程池一样）
### 4.1 场景描述
逐个提交任务，取结果。API 和线程池**完全一致**。

```plain
with ProcessPoolExecutor(max_workers=4) as pool:
    futures = [pool.submit(is_prime, n) for n in [7, 10, 13, 100]]
    for n, f in zip([7, 10, 13, 100], futures):
        print(f"  {n} 是质数吗? {f.result()}")
```

### 4.2 运行结果
```plain
--- submit: 提交任务取结果 ---
  7 是质数吗? True
  10 是质数吗? False
  13 是质数吗? True
  100 是质数吗? False
```

### 4.3 强调 API 一致性
| API | 线程池 | 进程池 |
| --- | --- | --- |
| `submit(fn, *args)` | ✅ | ✅ |
| `future.result()` | ✅ | ✅ |
| `map(fn, iterable)` | ✅ | ✅ |
| `as_completed(futures)` | ✅ | ✅ |
| `with ...`自动关闭 | ✅ | ✅ |

**唯一区别**：函数必须可 pickle（进程池约束）。用法层面完全一样。

## 五、案例 3：对比——CPU 密集任务，进程池 vs 线程池
### 5.1 这是全章的高潮：用实验证明 GIL 的存在
同样的 4 个重计算任务，分别用线程池和进程池跑，对比耗时。

```python
workload = [5_000_000] * 4   # 4 个相同的重计算

# 线程池
start = time.perf_counter()
with ThreadPoolExecutor(max_workers=4) as pool:
    list(pool.map(heavy_cpu, workload))
t_thread = time.perf_counter() - start

# 进程池
start = time.perf_counter()
with ProcessPoolExecutor(max_workers=4) as pool:
    list(pool.map(heavy_cpu, workload))
t_process = time.perf_counter() - start

print(f"  进程池快了约 {t_thread / t_process:.1f} 倍")
```

### 5.2 运行结果（4 核示例）
```plain
--- CPU 密集: 进程池 vs 线程池 ---
  线程池耗时: 3.200s  (受 GIL 限制, 实际串行)
  进程池耗时: 0.850s  (真并行)

  进程池快了约 3.8 倍
```

### 5.3 为什么差距这么大？
```plain
线程池（4 线程，1 把 GIL）：
  线程1 [====]
  线程2      [====]   ← 轮流抢 GIL, 实际串行
  线程3           [====]
  线程4                [====]
  总计 ≈ 4 个任务串行时间（甚至更慢，有切换开销）

进程池（4 进程，4 把独立 GIL）：
  进程1 [====]
  进程2 [====]   ← 各占一个核, 真并行
  进程3 [====]
  进程4 [====]
  总计 ≈ 1 个任务时间
```

**这就是第 01 章 GIL 结论的实证**：CPU 密集任务，多线程受 GIL 限制无法并行，多进程才能真并行。4 核机器上理论上快约 4 倍，实测 3.8 倍（有进程创建开销和调度损耗）。

## 六、使用准则与常见误区
### 6.1 max_workers 怎么设？
| 任务类型 | 建议 max_workers | 原因 |
| --- | --- | --- |
| **CPU 密集** | 默认（= CPU 核心数） | 正好吃满多核，多了只会切换 |
| 特殊场景 | 一般不超过核心数 | 超过核心数不会更快，反而增加调度开销 |

**和线程池不同**：线程池的 `max_workers` 在 I/O 密集时可以设很大（几十），因为线程在等 I/O 时会让出 GIL。但**进程池的 **`**max_workers**`** 不该超过 CPU 核心数**，因为进程是实打实占核的。

### 6.2 常见误区
| 误区 | 纠正 |
| --- | --- |
| "进程池的 `max_workers`设越大越快" | 进程是占核的，超过核心数只会频繁切换，**默认值就是最优** |
| "进程池能传 lambda" | 进程池要 pickle 函数，**lambda/嵌套函数/类方法都不行**，必须模块顶层函数 |
| "进程池适合 I/O 密集" | 进程太重，I/O 密集用线程池或协程，进程池只适合 CPU 密集 |
| "进程池和线程池可以随便换" | API 一样，但**适用场景相反**，换错了性能反而更差 |
| "传大对象给进程池没关系" | 参数和结果都要序列化，大对象开销巨大，尽量传小数据 |
| "Windows 上不写 `__main__`也能跑" | 和第 06 章一样，Windows 必崩，永远写保护 |

## 七、总结
### 7.1 核心要点
+ `ProcessPoolExecutor` → 进程池，**CPU 密集首选**
+ 用法和 `ThreadPoolExecutor`**完全一样**：`map` / `submit` / `as_completed`
+ `max_workers`**默认 = CPU 核心数**，别设超过核心数
+ 传参函数**必须是顶层函数**（能 pickle）

### 7.2 四条铁律
1. **CPU 密集 → **`**ProcessPoolExecutor**`
2. **I/O 密集 → **`**ThreadPoolExecutor**`
3. **传参函数必须是顶层函数（能 pickle）**
4. **Windows 上代码放 **`**if __name__ == "__main__":**`** 里**

### 7.3 一张图记住选型
```plain
任务类型？
├─ CPU 密集（算数/图像/加密）→ ProcessPoolExecutor（多进程，独立 GIL，真并行）
└─ I/O 密集（网络/磁盘/sleep）→ ThreadPoolExecutor（多线程，等 I/O 时释放 GIL）
```

### 7.4 与线程池的对照记忆
```plain
线程池：共享内存 + 共用 GIL + 函数随便传 → I/O 密集
进程池：独立内存 + 独立 GIL + 函数要 pickle → CPU 密集
API 一模一样，只是"执行器"换了，选对了才快。
```

# 09 协程基础
## 一、为什么需要协程？
### 1.1 线程池的局限
线程池（第 05 章）处理 I/O 密集已经不错了，但**并发量极大时（上万连接）**会暴露问题：

| 问题 | 说明 |
| --- | --- |
| **线程开不了这么多** | 每个线程要预留栈空间（Linux 约 8MB、Windows 约 1MB，是虚拟地址预留而非实际占用），1 万线程就是几十 GB 地址空间，直接爆 |
| **切换开销大** | 线程由操作系统调度，切换要进内核态，开销大 |

### 1.2 协程的思路
**协程 = 单线程内的"用户态切换"，开销极小，一个线程能调度上万任务。**

+ 切换在**用户态**完成，不进内核，开销极小
+ 一个线程就能调度上万协程，内存占用小
+ 适合**海量 I/O 并发**（Web 服务器、爬虫、网关）

### 1.3 核心概念速查
| 概念 | 解释 |
| --- | --- |
| `async def` | 定义一个协程函数 |
| `await` | 等待一个协程完成（挂起当前协程，让出控制权） |
| `asyncio.run()` | 启动事件循环，运行一个协程（程序入口） |
| `create_task()` | 把协程包装成 Task，立即调度执行 |
| `asyncio.gather()` | 并发运行多个协程，按输入顺序返回结果 |
| `asyncio.sleep()` | 非阻塞的 sleep（协程版） |
| `async for` | 异步迭代 |
| `async with` | 异步上下文管理器 |

### 1.4 最关键的区别（全章主线）
```plain
time.sleep(1)      → 阻塞，卡死整个事件循环
asyncio.sleep(1)   → 非阻塞，让出控制权给其他协程
```

**这句话是整章的灵魂**，后面案例 5 会专门对比演示。

## 二、事件循环：协程背后的发动机
### 2.1 一句话定义
**事件循环 = 一个单线程的无限循环，不停问："有没有任务准备好了？准备好了就执行；没准备好就等 I/O，等到了再回来。"**

它是**单线程**的，但通过"挂起 + 恢复"让多个协程交替执行，实现并发。

### 2.2 生活类比：一个服务员管多桌
+ 服务员 = 事件循环（单线程）
+ 顾客点菜 = 协程任务
+ 等厨房做菜 = I/O 等待（`await asyncio.sleep`）

服务员的做法：

```plain
1. A 桌点菜 → 单子交给厨房 → 不等菜好，去 B 桌
2. B 桌点菜 → 单子交给厨房 → 不等，去 C 桌
3. C 桌点菜 → 单子交给厨房 → 不等，回头看谁好了
4. A 的菜好了 → 端给 A；B 的好了 → 端给 B …循环
```

**关键**：服务员从不等菜做好（不阻塞），交完单子就干别的——这就是协程并发。

+ 服务员傻等 A 的菜好才去 B 桌（`time.sleep`）→ 串行，卡死
+ 服务员交完单子就下一桌（`await asyncio.sleep`）→ 三桌同时做菜，并发

### 2.3 事件循环内部在干什么？
```plain
while True:
    ready_tasks = 找出就绪的任务()      # 定时器到期、I/O 完成
    for task in ready_tasks:
        task.run_until_await()          # 跑到下一个 await 就停
    if not ready_tasks:
        wait_for_io_or_timer()          # 底层 epoll/kqueue，不占 CPU
```

三个动作：**就绪检查 → 执行 → 等待**。

### 2.4 为什么 time.sleep 会卡死？
+ `time.sleep` 是**真阻塞**：事件循环在这一步停摆，回不到 `while` 顶部去调度别的协程
+ `asyncio.sleep` 是**注册定时器 + 挂起**：事件循环继续转，到点再恢复

这就是案例 5（`sleep`）要演示的核心，先在这里建立认知。

### 2.5 asyncio.run() 做了什么？
```plain
asyncio.run(main())
# 等价于：
loop = asyncio.new_event_loop()      # 创建事件循环
loop.run_until_complete(main())      # 跑 main() 直到完成
loop.close()                         # 关闭
```

**程序入口**，一个线程同一时刻只能有一个运行中的事件循环。

### 2.6 三个唤醒源
| 唤醒源 | 例子 | 底层机制 |
| --- | --- | --- |
| 定时器到期 | `asyncio.sleep(1)` | 最小堆定时器 |
| I/O 就绪 | 网络数据到达 | `epoll`/`kqueue`/`select` |
| 新任务调度 | `create_task` | 就绪队列 |

### 2.7 事件循环 vs 线程 vs 进程
| 维度 | 事件循环（协程） | 线程 | 进程 |
| --- | --- | --- | --- |
| 调度者 | 用户态（事件循环） | 操作系统内核 | 操作系统内核 |
| 切换开销 | 极小 | 中 | 大 |
| 并发上限 | 上万 | 几十~几百 | 核心数 |
| 是否并行 | 否（单线程并发） | 否（受 GIL） | 是 |

**记住**：事件循环的"用户态调度"是协程轻量的根本原因。

## 三、案例 1：最基本的协程——async def + await + asyncio.run
### 3.1 场景描述
定义一个协程函数，用 `await` 等待它完成，用 `asyncio.run()` 启动。

```plain
async def greet(name):
    print(f"  开始问候 {name}")
    await asyncio.sleep(0.5)      # 非阻塞等待
    print(f"  问候 {name} 完成")
    return f"Hello, {name}"

async def main():
    result = await greet("Alice")
    print(f"  返回值: {result}")

asyncio.run(main())               # 程序入口: 启动事件循环
```

### 3.2 运行结果
```plain
--- 基础: async def + await ---
  开始问候 Alice
  问候 Alice 完成
  返回值: Hello, Alice
```

### 3.3 三个关键点
| 语法 | 作用 |
| --- | --- |
| `async def` | 定义一个**协程函数**（调用它返回协程对象，不立即执行） |
| `await` | 等待一个协程完成，**挂起当前协程，让出控制权**给事件循环 |
| `asyncio.run(main())` | **程序入口**：启动事件循环，运行 `main()`<br/> 协程，直到完成 |

### 3.4 重要理解：`async def` 函数调用后不会立即执行
```plain
coro = greet("Alice")   # 只是创建协程对象，不会执行！
# 必须 await coro 或 asyncio.run(coro) 才会真正跑
```

这和普通函数不同：普通函数调用就执行，协程函数调用只是"打包"，要 `await` 才跑。

### 3.5 执行流程
```plain
asyncio.run(main())
  └─ 启动事件循环
       └─ 运行 main()
            └─ await greet("Alice")
                 ├─ 打印"开始问候"
                 ├─ await asyncio.sleep(0.5)  → 挂起 greet，让出控制权
                 │    （事件循环空闲 0.5s，可以去跑别的协程）
                 ├─ 0.5s 后恢复 greet
                 ├─ 打印"问候完成"
                 └─ 返回 "Hello, Alice"
            └─ 打印返回值
```

## 四、案例 2：gather——并发运行多个协程（保序返回）
### 4.1 场景描述
三个协程耗时不同（A=1s、B=2s、C=0.5s），用 `gather` 并发运行。

```plain
async def fetch(name, delay):
    await asyncio.sleep(delay)
    return f"{name} (耗时 {delay}s)"

async def main():
    start = time.perf_counter()
    results = await asyncio.gather(
        fetch("A", 1),
        fetch("B", 2),
        fetch("C", 0.5),
    )
    print(f"  结果: {results}")
    print(f"  总耗时: {time.perf_counter() - start:.2f}s")
```

### 4.2 运行结果
```plain
--- gather: 并发运行, 按输入顺序返回 ---
  结果: ['A (耗时 1s)', 'B (耗时 2s)', 'C (耗时 0.5s)']
  总耗时: 2.00s  (并发, 约 2s 不是 3.5s)
```

### 4.3 两个关键理解
**理解 1：为什么是 2s 不是 3.5s？**

三个协程**并发**运行：

```plain
时间轴:
  A: [1s]
  B: [2s]        ← 最长的决定总耗时
  C: [0.5s]
  总耗时 = max(1, 2, 0.5) = 2s
```

`gather` 把三个协程**同时**丢进事件循环，它们交替执行，总耗时 = 最慢的那个，而不是总和。

**理解 2：为什么结果顺序是 A、B、C？**

`gather`**保序**：返回结果的顺序 = 输入顺序，**不是**完成顺序。虽然 C 最先完成（0.5s），但结果里 C 仍排第三。

**对比第 09 章**：进阶篇的 `as_completed` 是**不保序**（谁先完成先返回）。`gather` 保序，`as_completed` 不保序，这是两者的核心区别。

### 4.4 gather 的定位
| 工具 | 顺序 | 适用 |
| --- | --- | --- |
| `asyncio.gather` | **保序** | 需要按固定顺序拿结果 |
| `asyncio.as_completed` | **不保序** | 谁先好先处理谁 |

## 五、三种并发执行方式---直接 await / create_task / gather
### 5.1 场景描述
前面案例 2 只用了 `gather`。实际上 asyncio 有**三种**让协程并发执行的方式，各有适用场景：

| 方式 | 写法 | 特点 | 适用 |
| --- | --- | --- | --- |
| **方式一：直接 await** | `r = await greet(...)` | **顺序执行**，不并发 | 任务有先后依赖 |
| **方式二：create_task** | `t = asyncio.create_task(...)` | **并发执行**，可逐个控制 | 需要单独管理每个任务 |
| **方式三：gather** | `await asyncio.gather(...)` | **批量并发**，保序返回 | 一批任务一起等结果 |

### 5.2 三种方式对比代码
```plain
async def greet(name):
    print(f"  开始问候 {name}")
    await asyncio.sleep(1)
    print(f"  问候 {name} 完成")
    return f"Hello, {name}"

# 方式一：直接 await（顺序执行）
r1 = await greet("Alice")
r2 = await greet("Bob")

# 方式二：create_task 并发执行
task1 = asyncio.create_task(greet("Charlie"))
task2 = asyncio.create_task(greet("Dave"))
r3 = await task1
r4 = await task2

# 方式三：asyncio.gather 批量并发
results = await asyncio.gather(
    greet("Eve"),
    greet("Frank"),
)
```

### 5.3 运行结果对比
```plain
--- 方式一：直接 await（顺序）---
  开始问候 Alice
  问候 Alice 完成      ← 等 Alice 完成
  开始问候 Bob
  问候 Bob 完成
  耗时: 2.00s

--- 方式二：create_task（并发）---
  开始问候 Charlie
  开始问候 Dave        ← 两个同时开始
  问候 Charlie 完成
  问候 Dave 完成
  耗时: 1.00s

--- 方式三：gather（并发）---
  开始问候 Eve
  开始问候 Frank
  问候 Eve 完成
  问候 Frank 完成
  耗时: 1.00s
```

### 5.4 三种方式的关键区别
**方式一：直接 await = 顺序执行**

```plain
r1 = await greet("Alice")   # 等 Alice 完全跑完
r2 = await greet("Bob")     # 才开始 Bob
```

+ 两个任务**串行**，总耗时 = 1s + 1s = 2s
+ 只有在前一个任务必须完成后才能开始下一个时，才用这种方式

**方式二：create_task = 并发执行，可逐个控制**

```plain
task1 = asyncio.create_task(greet("Charlie"))  # 立即开始调度
task2 = asyncio.create_task(greet("Dave"))     # 立即开始调度
r3 = await task1    # 等 task1
r4 = await task2    # 等 task2
```

+ `create_task` 会**立即把协程包装成 Task 并丢进事件循环**开始执行
+ 两个任务**并发**，总耗时 = 1s
+ 可以**逐个 await**，适合"需要分别处理每个任务结果"的场景
+ 还可以对单个 task 做 `task.cancel()`、查 `task.done()` 等操作

**方式三：gather = 批量并发，保序返回**

```plain
results = await asyncio.gather(
    greet("Eve"),
    greet("Frank"),
)
```

+ 一行代码并发多个协程，**保序返回**结果列表
+ 适合"一批任务，只要结果"的场景
+ 内部其实也会包装成 Task，只是帮你省了手动步骤

### 5.5 create_task 和 gather 的底层关系
`**gather**`** 内部就是把每个协程用 **`**create_task**`** 包装成 Task，然后一起等。**

```plain
# gather 大致等价于：
tasks = [asyncio.create_task(greet("Eve")), asyncio.create_task(greet("Frank"))]
results = await asyncio.gather(*tasks)
```

所以：

+ **要单独控制每个任务** → 手动 `create_task`
+ **只要批量等结果** → 用 `gather`（更简洁）

### 5.6 create_task 的额外能力
`create_task` 返回的 `Task` 对象比 `gather` 更"可操作"：

| 操作 | 说明 |
| --- | --- |
| `task.cancel()` | 取消任务 |
| `task.done()` | 任务是否完成 |
| `task.cancelled()` | 任务是否被取消 |
| `task.result()` | 取结果（类似 Future） |
| `task.exception()` | 取异常 |

**典型场景**：先启动一批任务，中途根据某个条件取消其中一部分。

### 5.7 选型建议
| 场景 | 用哪个 |
| --- | --- |
| 任务有先后依赖 | 方式一：直接 `await` |
| 需要单独控制/取消任务 | 方式二：`create_task` |
| 一批任务批量等结果 | 方式三：`gather`（最常用） |

## 六、异常处理——默认抛出 vs return_exceptions=True
### 6.1 场景描述
并发任务中，某个任务抛异常怎么办？`gather` 有两种行为，通过 `return_exceptions` 控制。

```python
async def risky_task(name, should_fail):
    await asyncio.sleep(0.5)
    if should_fail:
        raise ValueError(f"{name} 失败了")
    return f"{name} 成功"
```

### 6.2 默认行为：第一个异常时抛出
```plain
try:
    results = await asyncio.gather(
        risky_task("A", False),
        risky_task("B", True),
    )
except ValueError as e:
    print(f"捕获异常: {e}")
```

**运行结果**：

```python
捕获异常: B 失败了
```

**关键理解**：

+ `gather`**默认**在第一个异常出现时**立即抛出**
+ 外层 `try/except` 能捕获
+ 但要注意：**其他任务并不会被自动取消**（它们仍在后台跑，只是结果丢了）——这是很多人的误区

### 6.3 return_exceptions=True：异常作为结果返回
```plain
results = await asyncio.gather(
    risky_task("D", False),
    risky_task("E", True),
    return_exceptions=True,
)
print(results)
```

**运行结果**：

```python
['D 成功', ValueError('E 失败了')]
```

**关键理解**：

+ `return_exceptions=True` 时，**异常不会抛出**，而是作为**结果列表的一项**返回
+ 成功的任务是正常值，失败的任务是异常对象
+ 适合"允许部分失败，需要知道每个任务的结果"的场景

### 6.4 两种行为对比
| 行为 | 默认（`return_exceptions=False`） | `return_exceptions=True` |
| --- | --- | --- |
| 异常处理 | 第一个异常立即抛出 | 异常作为结果返回 |
| 能否拿到其他任务结果 | ❌ 拿不到 | ✅ 能拿到全部 |
| 适合场景 | "一个失败就全盘失败" | "允许部分失败，逐个处理" |
| 外层写法 | 需要 `try/except` | 不需要 `try/except`，检查结果类型 |

### 6.5 处理 return_exceptions=True 的结果
因为结果列表里可能混着正常值和异常对象，需要**逐个判断类型**：

```plain
results = await asyncio.gather(
    risky_task("D", False),
    risky_task("E", True),
    return_exceptions=True,
)

for i, r in enumerate(results):
    if isinstance(r, Exception):
        print(f"  任务 {i} 失败: {r}")
    else:
        print(f"  任务 {i} 成功: {r}")
```

**运行结果**：

```plain
任务 0 成功: D 成功
  任务 1 失败: E 失败了
```

### 6.6 重要提醒：默认模式下其他任务不会取消
```plain
try:
    results = await asyncio.gather(
        risky_task("A", False),
        risky_task("B", True),
        risky_task("C", False),
    )
except ValueError as e:
    print(f"捕获异常: {e}")
    # 此时 A 和 C 可能还在后台跑！结果丢了
```

**如果希望"一个失败就取消所有"**，需要手动处理：

```plain
tasks = [asyncio.create_task(risky_task("A", False)),
         asyncio.create_task(risky_task("B", True)),
         asyncio.create_task(risky_task("C", False))]
try:
    results = await asyncio.gather(*tasks)
except ValueError:
    for t in tasks:
        t.cancel()   # 手动取消剩余任务
    raise
```

**对比第 05 章线程池**：线程池的异常存进 `Future`，在 `result()` 时抛出；`gather` 默认在第一个异常时抛出，但**不自动取消其他任务**。这是协程和线程池在异常处理上的重要区别。

## 七、案例 3：阻塞 vs 非阻塞——time.sleep vs asyncio.sleep
### 7.1 这是全章最重要的案例
同样 3 个"1 秒"任务，分别用 `time.sleep`（错误）和 `asyncio.sleep`（正确）跑，看差距。

```plain
async def blocking_demo():
    start = time.perf_counter()
    for i in range(3):
        time.sleep(1)             # 阻塞! 卡死事件循环
        print(f"  第 {i+1} 次完成")
    print(f"  总耗时: {time.perf_counter() - start:.2f}s")

async def nonblocking_demo():
    start = time.perf_counter()
    await asyncio.gather(
        asyncio.sleep(1),
        asyncio.sleep(1),
        asyncio.sleep(1),
    )
    print(f"  总耗时: {time.perf_counter() - start:.2f}s")
```

### 7.2 运行结果
```plain
--- 错误示范: 协程里用 time.sleep ---
  第 1 次完成
  第 2 次完成
  第 3 次完成
  总耗时: 3.00s (串行 3s)

--- 正确示范: 用 asyncio.sleep ---
  总耗时: 1.00s (并发 1s)
```

### 7.3 为什么差 3 倍？
**错误示范（**`**time.sleep**`**）**：

```plain
事件循环线程:
  time.sleep(1)  ← 真阻塞! 事件循环停摆 1 秒，其他协程全没法跑
  time.sleep(1)  ← 再停 1 秒
  time.sleep(1)  ← 再停 1 秒
  总耗时 = 3 秒（串行）
```

**正确示范（**`**asyncio.sleep**`**）**：

```plain
事件循环线程:
  gather 把 3 个 sleep 同时丢进去 → 都挂起，让出控制权
  （事件循环空闲，等 1 秒）
  1 秒后 3 个协程同时恢复
  总耗时 = 1 秒（并发）
```

### 7.4 核心结论
| 写法 | 行为 | 结果 |
| --- | --- | --- |
| `time.sleep(1)` | **阻塞**，事件循环停摆 | 串行，卡死其他协程 |
| `asyncio.sleep(1)` | **非阻塞**，挂起当前协程让出控制权 | 并发，其他协程能跑 |

**诊断技巧**：如果发现 asyncio 程序"看起来并发了，但实际是串行的"，第一反应就是检查——**有没有在协程里直接调 **`**time.sleep**`** 或其他阻塞函数**。

## 八、案例 4：async for / async with
### 8.1 场景描述
异步版本的 `for` 和 `with`——迭代/上下文管理的过程中可以 `await`。

```plain
async def async_range(n):
    """一个异步迭代器: 每次 yield 前 await 一下"""
    for i in range(n):
        await asyncio.sleep(0.2)
        yield i

class AsyncResource:
    """一个异步上下文管理器"""
    async def __aenter__(self):
        print("  打开资源")
        await asyncio.sleep(0.1)
        return self

    async def __aexit__(self, exc_type, exc, tb):
        print("  关闭资源")
        await asyncio.sleep(0.1)
```

### 8.2 运行结果
```plain
--- async for: 异步迭代 ---
  拿到 0
  拿到 1
  拿到 2

--- async with: 异步上下文管理器 ---
  打开资源
  资源使用中...
  关闭资源
```

### 8.3 async for 是什么？
普通 `for` 迭代一个**同步可迭代对象**；`async for` 迭代一个**异步可迭代对象**，每次迭代可以 `await`。

```plain
# 普通 for
for i in range(3):
    ...

# async for：每次迭代内部可以 await
async for i in async_range(3):
    ...
```

**典型场景**：异步读取数据库游标、异步分页拉取 API、异步读大文件。

### 8.4 async with 是什么？
普通 `with` 用 `__enter__`/`__exit__`；`async with` 用 `__aenter__`/`__aexit__`（都是 `async def`，内部可以 `await`）。

```plain
# 普通 with
with open(...) as f:
    ...

# async with：进入/退出时可以 await
async with aiohttp.ClientSession() as session:
    ...
```

**典型场景**：`aiohttp.ClientSession`、`aiomysql` 连接、异步锁/信号量（`asyncio.Lock`、`asyncio.Semaphore`）。

### 8.5 三者对照
| 同步版 | 异步版 | 用途 |
| --- | --- | --- |
| `for` | `async for` | 迭代可迭代对象 |
| `with` | `async with` | 上下文管理 |
| `def` | `async def` | 定义函数 |
| 直接调用 | `await` | 等待结果 |

## 十、常见误区与注意事项
| 误区 | 纠正 |
| --- | --- |
| "`async def`函数调用就执行" | 调用只返回**协程对象**，必须 `await`或 `asyncio.run()`才执行 |
| "协程里可以随便调 `time.sleep`" | 会**卡死整个事件循环**，必须用 `asyncio.sleep` |
| "`gather` 按完成顺序返回" | `gather`**保序**（按输入顺序），`as_completed`才按完成顺序 |
| "协程是并行的" | 协程是**单线程并发**（交替执行），不是并行（同时执行） |
| "协程能加速 CPU 密集" | 协程是单线程，CPU 密集用进程池（第 08 章） |
| "`async for`和普通 `for`一样" | `async for`迭代异步可迭代对象，每次迭代可 `await` |

| "直接 `await`两个协程就能并发" | 直接 `await`是**顺序执行**，要并发用 `create_task`或 `gather` |
| --- | --- |
| "`create_task` 和 `gather` 完全一样" | `create_task`返回单个 Task 可单独控制；`gather`是批量等待，更简洁 |
| "`gather` 默认会取消其他任务" | **不会**，默认只在第一个异常时抛出，其他任务仍在后台跑 |
| "`return_exceptions=True` 是让异常不抛" | 更准确说，是**把异常当结果返回**，需要自己判断类型处理 |

## 十一、总结
### 11.1 核心要点
+ **事件循环** → 单线程发动机，靠挂起/恢复实现并发（第二章）
+ `async def` → 定义协程函数（调用返回协程对象，不立即执行）
+ `await` → 等待协程完成，挂起当前协程
+ `asyncio.run()` → 启动事件循环（程序入口）
+ `create_task` → 包装成 Task，立即调度（可单独控制）
+ `asyncio.gather` → 并发运行多个协程，**保序**返回
+ `asyncio.sleep` → **非阻塞** sleep（协程版）
+ `async for/with` → 异步迭代 / 异步上下文管理器

### 11.2 三种并发方式 + 异常处理
```python
三种并发方式:
  直接 await    → 顺序执行（有依赖时用）
  create_task  → 并发，可单独控制（要取消/查状态时用）
  gather       → 批量并发，保序返回（最常用）

异常处理:
  gather 默认            → 第一个异常立即抛出（其他任务不取消）
  return_exceptions=True → 异常作为结果返回（适合部分失败）
```

### 11.3 三句话记住协程基础
1. `**async def**`** 定义、**`**await**`** 等待、**`**asyncio.run**`** 启动**
2. **协程里绝不用 **`**time.sleep**`**，要用 **`**asyncio.sleep**`**（否则卡死事件循环）**
3. `**gather**`** 并发 + 保序，总耗时 = 最慢的那个，不是总和**

### 11.4 一条铁律（贯穿整个协程系列）
**协程里绝不直接调 **`**time.sleep()**`** 等阻塞函数，否则卡死事件循环。**

这条铁律在基础篇（本章案例 3）讲，在进阶篇（09 章案例 3/4）还会用 `to_thread` 深化。

# 10 协程进阶 asyncio 生态+线程/进程混用
## 一、前置说明
### 1.1 核心概念速查
| 工具 | 作用 |
| --- | --- |
| `asyncio.as_completed()` | 谁先完成先处理谁 |
| `asyncio.timeout()` | 给一段协程设超时（3.11+） |
| `asyncio.to_thread()` | 把阻塞函数丢到线程池跑（不阻塞事件循环） |
| `loop.run_in_executor()` | 同上，可指定线程池/进程池 |

### 1.2 协程最大的坑（全章主线）
`**async def**`** 里如果调用了 **`**time.sleep()**`** 或 **`**requests.get()**`** 这类"阻塞"函数，整个事件循环都会被卡住，其他协程全没法跑。**

正确做法：

+ 有 async 版本的库（`aiohttp`、`aiomysql`）→ 用 `await`
+ 没有 async 版本的阻塞库 → `asyncio.to_thread()` 包一层
+ CPU 密集 → `run_in_executor()` 丢进程池

**这句话是整章的灵魂，后面所有案例都在围绕它展开。**

## 二、案例 1：asyncio.as_completed——谁先完成先处理
### 2.1 场景描述
三个任务耗时不同（A=2s、B=0.5s、C=1s），希望**按完成顺序**处理，而不是按提交顺序。

```plain
async def fetch(name, delay):
    await asyncio.sleep(delay)
    return f"{name} (耗时 {delay}s)"

async def run():
    tasks = [fetch("A", 2), fetch("B", 0.5), fetch("C", 1)]
    for coro in asyncio.as_completed(tasks):
        result = await coro
        print(f"  先完成的: {result}")
```

### 2.2 运行结果
```plain
--- asyncio.as_completed: 谁先完成先打印 ---
  先完成的: B (耗时 0.5s)
  先完成的: C (耗时 1s)
  先完成的: A (耗时 2s)
```

### 2.3 原理
+ `asyncio.as_completed(tasks)` 返回一个**异步迭代器**
+ 每次 `await` 拿到的是**下一个完成的**任务结果
+ 顺序 = 完成顺序，**不保序**

**对比第 05 章线程池**：`concurrent.futures.as_completed` 是同步迭代器，`asyncio.as_completed` 是异步迭代器。名字一样，作用一样——谁先完成先返回谁。区别只在"同步 vs 异步"。

### 2.4 和 gather 的区别
| 工具 | 顺序 | 何时用 |
| --- | --- | --- |
| `asyncio.gather` | **保序**（按提交顺序返回） | 需要按固定顺序拿结果 |
| `asyncio.as_completed` | **不保序**（按完成顺序） | 谁先好先处理谁 |

## 三、案例 2：超时控制——asyncio.timeout
### 3.1 场景描述
一个任务要跑 10 秒，但我们只等 1 秒，超时就放弃。

```plain
async def slow_task():
    await asyncio.sleep(10)
    return "太慢了"

async def run():
    try:
        async with asyncio.timeout(1):
            result = await slow_task()
            print(f"  完成: {result}")
    except TimeoutError:
        print("  超时了! 任务没在 1 秒内完成")
```

### 3.2 运行结果
```plain
--- 超时控制 ---
  超时了! 任务没在 1 秒内完成
```

### 3.3 关键点
+ `asyncio.timeout(秒)` 是 **Python 3.11+** 的新 API，用 `async with` 包裹
+ 超时后抛 `TimeoutError`（注意：不是 `asyncio.TimeoutError`，3.11 起统一为内置 `TimeoutError`）
+ 超时会**自动取消**块内正在运行的协程，不会泄漏任务

### 3.4 3.11 之前的写法（兼容说明）
```plain
# 3.11 之前
try:
    await asyncio.wait_for(slow_task(), timeout=1)
except asyncio.TimeoutError:
    ...
```

`wait_for` 仍在，但新代码推荐用 `asyncio.timeout`，因为它能包裹**一整段代码**（多个 await），而不只是单个协程。

## 四、案例 3：协程里调用阻塞函数——asyncio.to_thread
### 4.1 场景描述
`blocking_io` 是一个阻塞函数（模拟 `requests.get` 或慢速文件读取），要在协程里并发调用 3 次。

```plain
def blocking_io(n):
    time.sleep(1)
    return f"阻塞操作 {n} 完成"

async def run():
    start = time.perf_counter()
    results = await asyncio.gather(
        asyncio.to_thread(blocking_io, 1),
        asyncio.to_thread(blocking_io, 2),
        asyncio.to_thread(blocking_io, 3),
    )
    print(f"  {results}")
    print(f"  总耗时: {time.perf_counter() - start:.2f}s")
```

### 4.2 运行结果
```plain
--- asyncio.to_thread: 阻塞函数丢线程池, 不卡事件循环 ---
  ['阻塞操作 1 完成', '阻塞操作 2 完成', '阻塞操作 3 完成']
  总耗时: 1.00s  (3 个阻塞任务并发, 约 1s)
```

### 4.3 原理：为什么 3 个 1 秒的任务只花 1 秒？
```plain
事件循环线程（主线程）：
  await gather(...) → 把 3 个 blocking_io 丢进线程池 → 自己空闲，事件循环继续转

线程池（后台线程）：
  线程1: blocking_io(1) [====1s====]
  线程2: blocking_io(2) [====1s====]   ← 三个线程并行阻塞
  线程3: blocking_io(3) [====1s====]

总耗时 ≈ 1s
```

关键：**阻塞发生在后台线程里，事件循环线程不被卡住**。三个线程各自 `sleep(1)`，互不影响，所以总耗时约 1 秒，而不是 3 秒。

### 4.4 和直接调用的区别
| 写法 | 效果 |
| --- | --- |
| `blocking_io(1)` 直接调用 | **卡死事件循环 1 秒**，其他协程全停 |
| `await asyncio.to_thread(blocking_io, 1)` | 丢到线程池，**事件循环不受影响** |

### 4.5 适用场景
+ 用了**不支持 async 的库**（`requests`、`pymysql`、`time.sleep`）
+ 必须调用某个阻塞函数，但不想卡事件循环
+ 文件读写（标准库的同步文件 API 是阻塞的）

## 五、案例 4：错误示范——在协程里直接调阻塞函数
### 5.1 场景描述
同样的 3 个阻塞任务，这次**不用 **`**to_thread**`**，直接调用**，看看会发生什么。

```plain
async def run():
    start = time.perf_counter()
    for i in range(3):
        blocking_io(i)      # 直接调用, 每次卡 1 秒
    print(f"  串行耗时: {time.perf_counter() - start:.2f}s")
```

### 5.2 运行结果
```plain
--- 错误示范: 在协程里直接 time.sleep ---
  串行耗时: 3.00s  (3 秒, 事件循环被卡)
  对比案例 3 的 to_thread 并发版本, 差距明显
```

### 5.3 为什么慢 3 倍？
+ `blocking_io` 里的 `time.sleep(1)` 是**阻塞调用**
+ 它在**事件循环线程**里执行，`sleep` 期间整个事件循环停摆
+ 其他协程（如果有）全都无法运行
+ 3 次调用只能串行，总耗时 3 秒

**对比案例 3：同样是 3 个 1 秒任务，用 **`**to_thread**`** 只花 1 秒，直接调用花 3 秒。**

### 5.4 教学价值
这个"错误示范"是整章最有教学价值的案例，建议**和案例 3 连着跑**：

```plain
案例 3（正确）: 1.00s
案例 4（错误）: 3.00s
```

学生亲眼看到 3 倍差距，立刻理解"为什么协程里不能直接调阻塞函数"。

**诊断技巧**：如果发现 asyncio 程序"看起来并发了，但实际是串行的"，第一反应就是检查——**有没有在协程里直接调阻塞函数**。

## 六、案例 5：run_in_executor——协程里跑 CPU 密集（用进程池）
### 6.1 场景描述
协程里要做 CPU 密集计算，需要丢到**进程池**（不是线程池，因为 CPU 密集受 GIL 限制）。

```plain
def cpu_heavy(x):
    total = 0
    for i in range(x):
        total += i
    return total

async def run():
    loop = asyncio.get_running_loop()
    result = await loop.run_in_executor(None, cpu_heavy, 5_000_000)
    print(f"  CPU 计算结果: {result}")
```

### 6.2 运行结果
```plain
--- run_in_executor: 协程里跑 CPU 密集 (用进程池) ---
  CPU 计算结果: 12499997500000
  (CPU 密集放进程池, I/O 密集放线程池, 协程只负责调度)
```

### 6.3 第一个参数 `None` 是什么意思？
`loop.run_in_executor(executor, fn, *args)` 的第一个参数是**执行器**：

| 传入 | 效果 |
| --- | --- |
| `None` | 用默认的 `ThreadPoolExecutor`（线程池） |
| `ProcessPoolExecutor()` | 用进程池 |
| `ThreadPoolExecutor()` | 指定线程池 |

**注意**：代码注释说"用进程池"，但实际传的是 `None`，即**默认线程池**。这在教学代码里是个小瑕疵——如果真要做 CPU 密集加速，应该显式传进程池：

```plain
from concurrent.futures import ProcessPoolExecutor

async def run():
    loop = asyncio.get_running_loop()
    with ProcessPoolExecutor() as pool:
        result = await loop.run_in_executor(pool, cpu_heavy, 5_000_000)
```

**讲课时可以点出这个细节**：注释和代码略有出入，正好借机强调"CPU 密集必须显式用进程池，`None` 默认是线程池，受 GIL 限制"。

### 6.4 run_in_executor vs to_thread
| 工具 | 默认执行器 | 能否指定进程池 | 适用 |
| --- | --- | --- | --- |
| `asyncio.to_thread(fn, *args)` | 线程池 | ❌ 不能 | 阻塞 I/O |
| `loop.run_in_executor(executor, fn, *args)` | 线程池 | ✅ 能 | I/O 或 CPU 密集 |

**简单记**：`to_thread` 是 `run_in_executor` 的**简化版**（只能线程池）；需要进程池时用 `run_in_executor`。

## 七、三者分工：协程、线程、进程怎么配合
### 7.1 一张图看懂分工
```plain
┌─────────────────────────────────────────────────┐
│  协程（asyncio）— 负责调度，不干重活              │
│  ├─ I/O 密集，有 async 库 → await（aiohttp 等）  │
│  ├─ 阻塞 I/O，无 async 库 → asyncio.to_thread    │
│  └─ CPU 密集 → run_in_executor + 进程池          │
└─────────────────────────────────────────────────┘
```

### 7.2 三种任务的处理方式
| 任务类型 | 处理方式 | 原因 |
| --- | --- | --- |
| **I/O 密集，有 async 库** | `await aiohttp.get(...)` | 原生异步，最高效 |
| **I/O 密集，无 async 库** | `await asyncio.to_thread(requests.get, ...)` | 丢线程池，不卡事件循环 |
| **CPU 密集** | `await loop.run_in_executor(process_pool, fn, ...)` | 丢进程池，绕过 GIL |

### 7.3 分工铁律（原文档总结）
```plain
- 协程里绝不直接调用阻塞函数（time.sleep / requests 等）
- 有 async 版本的库（aiohttp 等）用 await
- 没有 async 版本的阻塞库 → asyncio.to_thread 包一层
- CPU 密集 → run_in_executor 丢进程池
```

### 7.4 三者的关系（帮助理解）
```plain
协程：轻量级调度单位，单线程内切换，适合高并发 I/O
线程：操作系统调度，适合阻塞 I/O（协程的好帮手）
进程：独立内存 + 独立 GIL，适合 CPU 密集（绕过 GIL）
```

**协程是"指挥官"，线程/进程是"干活的士兵"**：协程负责高效调度，遇到阻塞/CPU 任务就派给线程/进程去干。

## 八、常见误区与注意事项
| 误区 | 纠正 |
| --- | --- |
| "用了 async/await 就自动并发了" | 如果里面调了阻塞函数，照样串行，甚至更慢 |
| "协程里可以随便调 `time.sleep`" | 会卡死整个事件循环，必须用 `asyncio.sleep`或 `to_thread` |
| "`as_completed`和 `gather`一样" | `gather`保序，`as_completed`按完成顺序，用途不同 |
| "`run_in_executor(None, ...)` 是进程池" | `None`是**默认线程池**，CPU 密集要显式传 `ProcessPoolExecutor` |
| "`to_thread` 能跑 CPU 密集" | 它用线程池，受 GIL 限制，CPU 密集要用 `run_in_executor` + 进程池 |
| "`asyncio.timeout` 所有版本都有" | 3.11+ 才有，旧版本用 `asyncio.wait_for` |

## 九、总结
### 9.1 核心要点
+ `asyncio.as_completed()` → 谁先完成先处理
+ `asyncio.timeout(秒)` → 超时保护（3.11+）
+ `asyncio.to_thread()` → 阻塞 I/O 函数丢线程池（不卡事件循环）
+ `run_in_executor()` → 阻塞/CPU 函数丢线程池或进程池

### 9.2 四句话记住本章
1. **协程里绝不直接调用阻塞函数**（`time.sleep`/`requests` 会卡死事件循环）
2. **有 async 版本就用 **`**await**`**，没有就 **`**to_thread**`** 包一层**
3. **CPU 密集用 **`**run_in_executor**`** + 进程池**（`None` 默认是线程池，别搞错）
4. **协程负责调度，线程/进程负责干活**

### 9.3 一个判断口诀
```plain
看到阻塞调用 → 问自己：它在事件循环里跑吗？
  ├─ 是 → 改用 await 或 to_thread
  └─ 否 → 没关系
```

# 11 并发选型决策树： 线程 / 进程 / 协程
## 一、为什么这章是"面试答案"？
这是 Python 并发面试的**高频题**。面试官问"什么时候用线程，什么时候用进程？"，考的不是背定义，而是你能不能**说清"在什么场景下选哪个方案，为什么"**。

本章就是把这套判断逻辑系统化，并配上可运行的对比实验，让结论有数据支撑。

### 1.1 核心判断标准只有一条
**任务到底是 I/O 密集还是 CPU 密集。**

所有选型都从这个判断出发。

## 二、完整决策树
```plain
                          你的任务
                             │
              ┌──────────────┴──────────────┐
              │ 第一步：时间花在哪？          │
              └──────────────┬──────────────┘
                             │
        ┌────────────────────┴────────────────────┐
        │                                         │
   I/O 密集                                   CPU 密集
  (等网络/磁盘/DB)                          (算数/图像/加密)
        │                                         │
        │                                         ├─ 数据量小、任务少 ─→ 直接同步跑
        │                                         │   (开进程反而更慢)
        │                                         │
        │                                         ├─ 数据量大、任务多
        │                                         │     │
        │                                         │     ├─ 任务间无依赖 ─→ 进程池
        │                                         │     │   ProcessPoolExecutor
        │                                         │     │
        │                                         │     └─ 任务间有依赖/需共享状态
        │                                         │         ─→ 多进程 + Queue/Manager
        │                                         │            (第 06/07 章)
        │                                         │
        │                                         └─ 可向量化计算 ─→ NumPy/Pandas
        │                                             (比多进程快得多)
        │
        ├─ 第二步：有异步库吗？
        │     │
        │     ├─ 有（aiohttp/httpx/aiomysql/asyncpg）
        │     │     │
        │     │     └─ 第三步：并发量？
        │     │           ├─ < 几十 ─→ 线程池也行，但协程更统一
        │     │           └─ ≥ 上百 ─→ asyncio + 异步库（无需框架）
        │     │
        │     └─ 没有（只有 requests/pymysql 等同步库）
        │           │
        │           └─ 第三步：能否换异步库？
        │                 ├─ 能换 ─→ 换异步库，走 asyncio
        │                 │
        │                 └─ 不能换（第三方 SDK 只有同步版）
        │                       │

        │                       │              或 loop.run_in_executor
        │                       │              (09 章)
        │                       │
        │                       └─ 不在协程里？
        │                             │
        │                             ├─ 并发量 < 几百 ─→ 线程池
        │                             │   ThreadPoolExecutor
        │                             │
        │                             └─ 并发量上千 ─→ 线程池 + 分批
        │                                 (max_workers=100~200)
        │
        └─ 第四步：已有 async 框架？
              ├─ 有（FastAPI/Sanic/aiohttp server）
              │   ─→ 直接 async def，框架已封装好
              │
              └─ 没有 ─→ 回到"有异步库吗"分支
```

## 三、逐步判断说明
### 3.1 第一步：I/O 密集 vs CPU 密集
| 特征 | I/O 密集 | CPU 密集 |
| --- | --- | --- |
| 时间花在哪 | 等网络、磁盘、数据库 | 算数、图像、加密 |
| CPU 占用 | 低（大部分时间在等） | 高（一直在算） |
| 典型任务 | HTTP 请求、文件读写、查库 | 图像处理、加密解密、科学计算 |
| 怎么判断 | `cProfile`看，`time.sleep`/`recv`占比高 | `cProfile`看，计算函数占比高 |

**判断技巧**：跑一下任务，看 CPU 占用率——**CPU 占用低但耗时长 = I/O 密集；CPU 占用高 = CPU 密集**。

### 3.2 CPU 密集的细分
| 子分支 | 判断 | 选型 | 原因 |
| --- | --- | --- | --- |
| 数据量小、任务少 | 总耗时 < 0.1s | **直接同步跑** | 开进程的开销（复制解释器）比计算本身还大 |
| 可向量化 | 能用 NumPy | **NumPy/Pandas** | 底层 C + SIMD，比多进程快得多 |
| 任务间无依赖 | 各算各的 | **进程池** | 并行吃满多核 |
| 任务间有依赖/需共享状态 | 要传数据 | **多进程 + Queue/Manager** | 进程不共享内存，要显式通信（第 06/07 章） |

**重要提醒**：很多"CPU 密集"任务其实**不该用多进程**，而该用 **NumPy 向量化**。比如"100 万个数各加 1"，多进程要序列化传输，NumPy 一行 `arr + 1` 就搞定，快几十倍。**先问"能不能向量化"，再考虑多进程。**

### 3.3 I/O 密集的细分
#### 分支 A：有异步库
| 子分支 | 判断 | 选型 |
| --- | --- | --- |
| 并发量 < 几十 | 少量连接 | 线程池也行，但协程更统一（一套代码走到底） |
| 并发量 ≥ 上百 | 大量连接 | **asyncio + 异步库**（无需框架） |

**为什么"有异步库时，并发量小也推荐协程"？** 如果项目已经引入了异步库，**统一用协程**比"小并发用线程、大并发用协程"两套代码更好维护。除非项目完全是同步风格，那线程池更简单。

#### 分支 B：没有异步库
| 子分支 | 判断 | 选型 |
| --- | --- | --- |
| 能换异步库 | 依赖的库有异步版 | **换异步库**，走 asyncio |
| 不能换（第三方 SDK 只有同步版） | 依赖锁死 | 看下面 |
| └ 在协程里 | 项目已经是 async | `**asyncio.to_thread**`<br/> 或 `**loop.run_in_executor**`<br/>（09 章） |
| └ 不在协程里 | 纯同步项目 | 看并发量 |
|    ├ 并发量 < 几百 | 中等并发 | **线程池**`ThreadPoolExecutor` |
|    └ 并发量上千 | 高并发 | **线程池 + 分批**（`max_workers=100~200`<br/>） |

### 3.4 第四步：已有 async 框架
| 子分支 | 选型 |
| --- | --- |
| 有（FastAPI/Sanic/aiohttp server） | **直接 **`**async def**`，框架已封装好路由 + 事件循环 |
| 没有 | 回到"有异步库吗"分支 |

**框架的价值**：它帮你把"事件循环 + 路由 + 异步处理"封装好了。有框架时，你只需要写 `async def`，不用关心 `asyncio.run` 在哪调。

## 四、关键子分支详解
### 4.1 "在协程里"遇到同步阻塞库怎么办？
**场景**：项目已经是 `async def` 风格（比如 FastAPI），但某个函数只有同步版（`requests`、`pymysql`），不能直接调——会卡死事件循环。

**错误写法**：

```plain
async def main():
    resp = requests.get("https://example.com")   # 卡死事件循环！
```

**正确写法一：**`**asyncio.to_thread**`**（简单，只能线程池）**

```plain
async def main():
    text = await asyncio.to_thread(requests.get, "https://example.com")
```

**正确写法二：**`**loop.run_in_executor**`**（灵活，可传进程池）**

```plain
async def main():
    loop = asyncio.get_running_loop()
    text = await loop.run_in_executor(None, requests.get, "https://example.com")
```

**两者区别**：

| 工具 | 默认执行器 | 能否指定进程池 | 版本 |
| --- | --- | --- | --- |
| `asyncio.to_thread` | 线程池 | ❌ | 3.9+ |
| `loop.run_in_executor` | 线程池 | ✅ | 更早就有 |

**重要提醒**：这是"退路"不是"首选"。**能换异步库（**`**aiohttp**`**/**`**httpx**`**）才是正解**——`to_thread` 底层还是线程池，受线程数限制；真正的异步库是纯事件循环驱动，能扛上万并发。

### 4.2 "线程池 + 分批"怎么写？
**纯同步写法，不用 asyncio**：

```plain
from concurrent.futures import ThreadPoolExecutor
import requests

def fetch(url):
    return requests.get(url).text

urls = [f"https://example.com/page/{i}" for i in range(10000)]

with ThreadPoolExecutor(max_workers=100) as pool:
    for i in range(0, len(urls), 100):        # 分批：每批 100 个
        batch = urls[i:i+100]
        results = list(pool.map(fetch, batch))  # 每批并发跑
```

**批大小怎么定？** 批大小 ≈ `max_workers`，让每批刚好跑满线程池。太大单批耗时长，太小批间串行开销累积。

### 4.3 "没有 async 框架"时海量 I/O 的三条路
| 路径 | 前提 | 并发上限 | 总耗时 | 代码复杂度 |
| --- | --- | --- | --- | --- |
| asyncio + 异步库 | 有异步库 | 上万 | 最短 | 中（要全异步） |
| async 框架 | 已有框架 | 上万 | 最短 | 低（框架封装好） |
| 线程池 + 分批 | 无异步库也行 | 100~200/批 | 较长（分批串行） | 低（同步代码） |

`**asyncio**`** 是标准库，不需要框架**。只要配合异步库（`aiohttp`/`httpx`），就能处理海量 I/O：

```plain
import asyncio
import aiohttp

async def fetch(session, url):
    async with session.get(url) as resp:
        return await resp.text()

async def main(urls):
    async with aiohttp.ClientSession() as session:
        tasks = [fetch(session, url) for url in urls]
        return await asyncio.gather(*tasks)   # 上万 URL 并发

asyncio.run(main(urls))   # 标准库，无需框架
```

## 五、量化标准（避免模糊）
| 术语 | 量化参考 | 说明 |
| --- | --- | --- |
| **并发量小** | < 几十（10~50） | 线程池足够，开协程反而增加复杂度 |
| **并发量中等** | 几十 ~ 几百 | 线程池能扛（`max_workers`设 100~200） |
| **并发量极大** | 上千 ~ 上万 | 线程开不了这么多，必须协程或分批 |
| **任务少** | < 10 个 | 直接同步跑，开池子不划算 |
| **任务多** | > 100 个 | 值得开池子 |

**注意**：这些数字是**经验值，不是硬标准**。实际要看机器配置、任务耗时、内存限制、可接受延迟。**先用小规模测试，再决定。**

## 六、三者对比表（面试直接背）
| 维度 | 线程 | 进程 | 协程 |
| --- | --- | --- | --- |
| **执行方式** | 并发（受 GIL） | 并行 | 并发（单线程） |
| **切换开销** | 中 | 大 | 极小 |
| **内存共享** | 是（要加锁） | 否（要通信） | 是（单线程，天然安全） |
| **适合** | I/O 密集 | CPU 密集 | 海量 I/O |
| **并发上限** | 几十~几百 | 核心数 | 上万 |
| **代表库** | `threading` | `multiprocessing` | `asyncio` |

**一句话记**：**线程"够用"、进程"能算"、协程"能扛"**。

## 七、案例 1：I/O 密集——线程池 vs 进程池
### 7.1 场景描述
8 个 I/O 任务（各 `sleep(0.5)`），分别用线程池和进程池跑。

```plain
def io_task(name):
    time.sleep(0.5)
    return f"{name} 完成"

tasks = [f"任务{i}" for i in range(8)]

with ThreadPoolExecutor(max_workers=4) as pool:
    list(pool.map(io_task, tasks))

with ProcessPoolExecutor(max_workers=4) as pool:
    list(pool.map(io_task, tasks))
```

### 7.2 运行结果
```plain
=== I/O 密集任务: 线程池 vs 进程池 ===

  线程池: 1.00s
  进程池: 1.05s
  结论: I/O 密集两者差不多, 但线程池更轻量 → 选线程池
```

### 7.3 为什么差不多？
+ I/O 任务的时间花在 `**sleep**`**（等 I/O）** 上
+ 等 I/O 时 **GIL 会释放**，线程池能并发
+ 进程池也能并行，但**进程创建开销更大**，所以略慢一点点
+ 综合来看：**I/O 密集选线程池**（够用 + 轻量）

## 八、案例 2：CPU 密集——线程池 vs 进程池
### 8.1 场景描述
4 个 CPU 密集任务（各 400 万次累加），分别用线程池和进程池跑。

```plain
def cpu_task(n):
    total = 0
    for i in range(n):
        total += i
    return total

workload = [4_000_000] * 4
```

### 8.2 运行结果（4 核示例）
```plain
=== CPU 密集任务: 线程池 vs 进程池 ===

  线程池: 1.20s  (GIL 限制, 实际串行)
  进程池: 0.35s  (真并行)
  结论: CPU 密集进程池完胜 → 选进程池
```

### 8.3 为什么差距这么大？
```plain
线程池（4 线程，共用 1 把 GIL）：
  线程1 [====]
  线程2      [====]   ← 轮流抢 GIL, 实际串行
  线程3           [====]
  线程4                [====]
  总耗时 ≈ 4 个任务之和（甚至更慢，有切换开销）

进程池（4 进程，4 把独立 GIL）：
  进程1 [====]
  进程2 [====]   ← 各占一个核, 真并行
  进程3 [====]
  进程4 [====]
  总耗时 ≈ 1 个任务时间
```

### 8.4 教学价值
这个实验直接印证了第 01 章 GIL 的结论：**CPU 密集任务，多线程受 GIL 限制无法并行，多进程才能真并行**。建议**现场跑给学生看**，比理论讲解直观得多。

## 九、案例 3：海量 I/O——线程池分批 vs asyncio（无框架）
### 9.1 场景描述
模拟 1000 个 I/O 任务（各 `sleep(0.01)`），对比两种方案：

+ **方案 A**：线程池 + 分批（`max_workers=100`）
+ **方案 B**：asyncio + `asyncio.sleep`（无框架）

```plain
# 方案 A：线程池 + 分批
def fetch_sync(n):
    time.sleep(0.01)
    return n

def demo_thread_batch():
    tasks = list(range(1000))
    start = time.perf_counter()
    with ThreadPoolExecutor(max_workers=100) as pool:
        for i in range(0, len(tasks), 100):
            list(pool.map(fetch_sync, tasks[i:i+100]))
    print(f"  线程池+分批: {time.perf_counter() - start:.2f}s")

# 方案 B：asyncio
async def fetch_async(n):
    await asyncio.sleep(0.01)
    return n

def demo_asyncio():
    async def run():
        tasks = [fetch_async(i) for i in range(1000)]
        await asyncio.gather(*tasks)
    start = time.perf_counter()
    asyncio.run(run())
    print(f"  asyncio: {time.perf_counter() - start:.2f}s")
```

### 9.2 运行结果（示例）
```plain
=== 海量 I/O: 线程池分批 vs asyncio ===

  线程池+分批: 0.15s
  asyncio:     0.02s
  结论: 海量 I/O 协程优势明显, 且无需框架
```

### 9.3 为什么 asyncio 更快？
+ **线程池**：每批 100 个任务，1000 个任务分 10 批，批与批之间串行，总耗时 ≈ 10 × 单批时间
+ **asyncio**：1000 个协程**同时**挂起在事件循环里，总耗时 ≈ 单个任务时间
+ 任务越多，差距越大

## 十、案例 4：面试问答速查
### 10.1 七道高频题
#### Q1: 说说 Python 的 GIL？
全局解释器锁，CPython 里同一时刻只允许一个线程执行字节码。导致多线程无法利用多核加速 CPU 密集任务；但 I/O 时会释放 GIL，所以多线程对 I/O 密集有效。想真正并行得用多进程。

#### Q2: 线程和进程的区别？
线程共享内存、轻量、受 GIL 限制；进程独立内存、重量、各自有 GIL 所以能并行。线程切换开销小，进程创建销毁开销大。

#### Q3: 协程和线程的区别？
协程是单线程内的用户态切换，无内核切换开销，极轻量；线程由操作系统调度，有切换开销。协程需要事件循环驱动，配合 async/await，适合海量 I/O 并发。

#### Q4: 什么时候用多进程？
CPU 密集任务（计算、图像处理、加密），因为线程受 GIL 限制无法并行，进程能绕过 GIL 真并行。

#### Q5: 什么时候用协程而不是线程？
需要同时处理成千上万个 I/O 连接时（如 Web 服务器、爬虫），协程切换开销极小，一个线程能调度海量任务，线程开不了这么多。

#### Q6: 没有 async 框架，海量 I/O 怎么办？
三条路：

① 标准库 `asyncio`+ 异步库（`aiohttp`/`httpx`），无需框架也能上万并发；

② 无异步库时用线程池 + 分批（`max_workers=100~200`）；

③ 已在协程里遇到同步库，用 `asyncio.to_thread`救急。

#### Q7: 协程里要调阻塞函数怎么办？
用 `asyncio.to_thread`或 `loop.run_in_executor`把它丢到线程池，不卡事件循环。但这是退路，能换异步库（`aiohttp`）才是首选。

### 10.2 回答技巧
+ **先给结论，再解释原因**：先说"用 X，因为 Y"
+ **结合 GIL 讲**：几乎所有回答都能落到 GIL 上
+ **给出具体场景**：说"CPU 密集"时举例（图像处理、加密）
+ **Q6/Q7 是加分项**：能说出"asyncio 是标准库，不需要框架"和"to_thread 是退路"，说明真懂

## 十一、一句话总结（面试记这句就够）
**"Python 的 GIL 导致多线程无法加速 CPU 计算，所以：**
**- CPU 密集：优先向量化（NumPy），否则进程池**
**- I/O 密集：并发量小用线程池；海量连接用协程（asyncio + 异步库，无需框架）；无异步库时线程池分批也能扛**
**- 协程里遇到同步阻塞库：用 to_thread / run_in_executor 救急，但换异步库才是正解"**

## 十二、选型总结与常见误区
### 12.1 选型五句话
```plain
1. CPU 密集 → 先问能否向量化（NumPy），否则进程池
2. I/O 密集 + 并发量一般 → 线程池 ThreadPoolExecutor
3. I/O 密集 + 海量 + 有异步库 → asyncio + 异步库（无需框架）
4. I/O 密集 + 海量 + 无异步库 → 线程池 + 分批
5. 协程里遇到同步阻塞库 → asyncio.to_thread / run_in_executor（救急）
```

### 12.2 常见误区
| 误区 | 纠正 |
| --- | --- |
| "多线程一定能加速" | 受 GIL 限制，CPU 密集多线程不但不加速，可能更慢 |
| "进程一定比线程好" | 进程重，I/O 密集用进程是杀鸡用牛刀 |
| "协程能替代一切" | 协程需要 async 生态配合，CPU 密集它也无能为力 |
| "并发量小也用协程" | 几十个连接用线程池足够，协程是"海量连接"才需要的重武器 |
| "用 asyncio 必须上框架" | `asyncio`是标准库，配 `aiohttp`等异步库即可 |
| "没有异步库就没法高并发" | 线程池 + 分批（`max_workers=100~200`）也能扛 |
| "`to_thread` 能扛上万并发" | `to_thread`底层是线程池，受线程数限制；上万并发要用异步库 |
| "CPU 密集都该用进程池" | 先问能否向量化（NumPy），数据量小时直接同步跑 |
| "选型看哪个'高级'用哪个" | 选型只看任务类型、并发量、有无异步库 |

## 十三、总结
### 13.1 本章的核心
+ **判断标准**：I/O 密集还是 CPU 密集
+ **CPU 密集**：先向量化，再进程池，数据小直接同步
+ **I/O 密集**：小并发线程池，海量有异步库用 asyncio，无异步库线程池分批
+ **协程里遇阻塞**：`to_thread` / `run_in_executor` 救急
+ **框架不是必需**：`asyncio` 是标准库

### 13.2 面试答题框架
```plain
第一步：判断任务类型（I/O 密集 or CPU 密集）
第二步：CPU 密集 → 向量化？ → 进程池？ → 数据量小直接同步
第三步：I/O 密集 → 看并发量
        - 几十 → 线程池
        - 上万 → 有异步库用 asyncio，无异步库用线程池分批
第四步：已在协程里遇同步库 → to_thread / run_in_executor
第五步：解释原因（落到 GIL、切换开销、内存共享上）
```

### 13.3 一句话收尾
**选型不是选"最强"的工具，而是选"最合适"的工具。判断依据永远是任务类型、并发量、有无异步库，不是工具的先进程度。框架不是必需的——**`**asyncio**`** 是标准库，异步库是普通第三方包，组合起来就能处理海量 I/O。**
